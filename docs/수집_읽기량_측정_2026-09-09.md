# 수집 회차가 데이터베이스에서 읽어 가는 양 (2026-09-09)

2026-09-09 Supabase 가 egress(데이터베이스에서 나간 데이터) 무료 한도 **월 5GB** 초과를
통지했다. 10월 9일부터 제한이 걸릴 수 있다. 이 문서는 두 가지를 다룬다.

- (A) 백업 주기를 6시간마다에서 **주 1회**로 바꾼 내용과 그 부작용
- (B) 수집 회차 한 번이 데이터베이스에서 읽어 가는 양의 **실측**과 줄일 방법

숫자는 모두 운영 데이터베이스에서 잰 것이다. 추정한 것은 추정이라고 적었고, 재지 못한
것은 마지막 절에 모아 두었다. **이 작업에서 운영 데이터베이스에 쓴 것은 없다**(측정
연결은 `default_transaction_read_only = on` 으로 열었다).

### 부작용: 복구 시 최대 7일치 운영 기록 손실

마지막 백업 이후에 생긴 것은 복원되지 않는다. 구체적으로는

- 실행 이력(`runs`, `source_runs`)
- 출처 상태(`source_health` — 재시도 위치, 백필 진행, 연속 실패 횟수)
- 중복 판정 기록(`dedupe_decisions`), 병합·되돌림 기록
- 감사 기록(`audit_logs`), 보정(`content_overrides`)

복구 뒤에는 출처 상태가 최대 일주일 전으로 돌아가므로 첫 회차가 그만큼 더 오래 걸린다.

**공지 자체는 백업이 아니어도 남는다.** 매시 수집이 공개용 JSON 전체 사본을 R2 공개
버킷에 올리고, 원문 증거는 증거 버킷에 남는다. 공지·본문·연락처는 R2 파일에서 되살릴 수
있고, 이 백업이 지키는 것은 위의 운영 기록 쪽이다.

### 보존 정책(`--prune`)은 바꾸지 않았다

`backend/app/run/backup.py` 의 `RECENT_DAYS = 7`, `DAILY_DAYS = 30` 을 그대로 두었다.
늘리면 탈퇴·삭제 요청이 백업에 남는 기간도 함께 늘어나기 때문이다(계획 17.2절).
주 1회로 바뀌면 실제로 남는 것은 **주 1개씩 4~5개**다.

2026-09-09 기준 백업 버킷에는 11개(2026-09-06 05:13Z ~ 2026-09-09 05:13Z)가 있다.
이 목록에 정책을 그대로 적용해 본 결과는 이렇다.

| 실행 시각(UTC) | 지워지는 백업 | 설명 |
|---|---|---|
| 2026-09-12 19:52 (첫 주 1회 실행) | **0개** | 모두 7일 안이다 |
| 2026-09-19 19:52 | 7개 | 09-06·09-07·09-08 의 같은 날짜 중복분(하루 1개만 남긴다) |
| 2026-09-26 19:52 | 0개 | 추가 삭제 없음 |

**주기를 바꿨다고 해서 지금 R2 에 있는 백업이 추가로 지워지지는 않는다.** 위 7개는 예전
6시간 주기에서도 8일째 되는 날 같은 규칙으로 지워질 것들이고, 주 1회가 되면서 오히려
더 늦게 지워진다. `--prune` 은 워크플로가 돌 때만 동작한다.

## (B) 수집 회차의 데이터베이스 읽기량

### 잰 방법

1. SQLAlchemy 의 `before_execute` 이벤트로 **수집 코드가 실제로 보낸 select 문**
   (ClauseElement)을 가로챈다. 이때는 문장만 모으고 결과는 쓰지 않는다.
2. 세션을 닫은 뒤 그 문장을 리터럴 바인딩으로 컴파일해

   ```sql
   select count(*), sum(octet_length(t::text)) from ( <가로챈 문장> ) t
   ```

   로 감싸 **서버에서** 행 바이트를 세게 한다. 본문(`body_html`/`body_text`)을 이쪽으로
   끌어오지 않고도 그 문장이 내보낼 바이트를 알 수 있다.
3. 회차당 실행 횟수는 `runs`·`source_runs` 에 남은 실측(`list_items`,
   `missing_check_performed` 등)에서 가져왔다. 목록 한 쪽분만 재고 450곳으로 곱하는
   외삽이 아니라, 기준 회차의 출처별 `list_items` 만큼을 **가로 조인(lateral)** 으로
   붙여 회차 전체를 한 번에 셌다.

측정 스크립트는 임시 폴더에만 두었고 저장소에 넣지 않았다. `backend/app/storage/db.py`
는 건드리지 않았다(다른 작업이 그 파일에 계측을 넣는 중이다).

**줄 번호에 관해.** 아래 표의 `파일:줄` 은 2026-09-09 15:50 KST 기준이다. 같은 시간에
다른 작업이 `run/collect.py`·`export/static.py`·`storage/db.py`·`ops/selfcheck.py` 를
고치는 중이라 줄 번호는 밀릴 수 있다. 함수 이름으로 찾는 편이 확실하다.

**근사치라는 점.** `row::text` 는 행을 Postgres 레코드 문자열로 만든 길이라 실제 전송
바이트와 같지 않다. 따옴표·이스케이프가 조금 더 붙고, 이진 형식과도 다르다. 이번
기준 회차에서 본문 원바이트 합은 11,360,204 B, 같은 행들을 문자열로 만들면
12,833,117 B 였으므로 이스케이프 덧붙음은 약 13% 다. 아래 표는 `row::text` 기준이라
**실제보다 조금 크게 잡은 값**으로 보면 된다.

### 자체 점검과 감시

- **자체 점검**(`.github/workflows/collect.yml` 의 「자체 점검」 단계, 매 회차 1회):
  데이터베이스 읽기는 합쳐 **101,121 B**. 가장 큰 것은 상세 실패 메시지 표본
  893행 71,459 B, 그다음이 「조용한 0건」 후보 43행 20,281 B 다. 「조용한 0건」의
  **원문 프로빙은 원문 서버에 대한 HTTP 요청**이라 Supabase egress 와 무관하다.
- **수집 감시**(`.github/workflows/watchdog.yml`, 15분마다): 데이터베이스 조회는
  `select max(started_at), max(finished_at) from runs where kind='collect'` **한 번,
  65 B** 뿐이다. 게다가 저장소 변수 `KHU_INITIAL_UNTIL` 이 비었거나 지났으면 「마감
  확인」 단계에서 끝나 의존성 설치도 하지 않고 데이터베이스를 아예 열지 않는다.
  최악의 경우(마감이 계속 살아 있음)에도 하루 96회 × 65 B = **약 6 KB** 다.

### 결론: 손댈 필요 **있음**

- **회차당 5 MB 를 넘는 쿼리가 하나 있다.** 1번 `preload_listing_items` 의 이력 조회,
  회차당 **12.83 MB**. 회차 전체 읽기량 16.65 MB 의 **77%** 다.
- 회차당 읽기량 16.65 MB × 하루 약 15.7회 ≈ **하루 182 MB** 로, 하루 총 egress 예산
  160 MB 를 수집 하나가 이미 넘는다. 매시 24회를 다 돌면 하루 400 MB 다.

## 줄이는 방법 (제안만, 코드는 고치지 않았다)

### 제안 1 — `preload_listing_items` 에서 본문 두 칸을 뺀다 · **정확도 손실 없음**

`backend/app/storage/repository.py:374`

```python
revisions = list(session.scalars(select(m.SourceItemRevision).where(
    m.SourceItemRevision.id.in_([item.current_revision_id for item in items if item.current_revision_id])
)))
```

`select(m.SourceItemRevision)` 은 매핑된 칸을 전부 가져온다. 여기에 `body_html`(평균
1,583 B)과 `body_text`(평균 691 B)가 들어 있다. **그런데 수집 경로는 이렇게 올린 기존
이력의 본문을 한 번도 읽지 않는다.** 확인한 사용처는 이것뿐이다.

| 읽는 곳 | 쓰는 칸 |
|---|---|
| `repository.py:403` `detail_is_due` | `title`, `published_raw`, `published_date` |
| `repository.py:537` `upsert_item_and_revision` | `content_hash`, `published_date/at/raw`, `board_category` (쓰기: `observed_at`, `raw_object_key`) |

공지 갱신(`upsert_notice_for_item` → `make_excerpt`, `_search_text`)과 중복 후보
만들기(`_to_candidate`)에 쓰는 이력은 **새로 만든 것**이거나(`collect.py:419`,
`collect.py:486`) **다른 조회가 따로 읽어 온 것**(`recent_items_for_dedupe`)이다.

**방법.** 다음 중 하나.

```python
from sqlalchemy.orm import defer
...
select(m.SourceItemRevision)
    .options(defer(m.SourceItemRevision.body_html), defer(m.SourceItemRevision.body_text))
    .where(...)
```

`defer` 를 쓰면 나중에 누가 그 칸을 만지더라도 SQLAlchemy 가 그때 한 번 더 읽어 온다.
동작은 그대로고 쿼리가 하나 늘 뿐이다. 필요한 칸만 `select` 하는 방법도 있지만 결과가
ORM 객체가 아니라 튜플이 되어 `detail_is_due`·`upsert_item_and_revision` 의 identity map
활용(같은 글을 다시 조회하지 않는 지금 구조)이 깨지므로 **`defer` 쪽을 권한다.**

**효과.** 회차당 12,833,117 B → **1,404,975 B**(실측). 회차당 **11.4 MB 절감(-89%)**,
하루 약 116 MB 절감.

**대가.** 없다고 본다. 굳이 적자면, 나중에 누군가 preload 로 올린 이력의 본문을 읽는
코드를 넣으면 그 자리에서 지연 조회가 한 번 난다(결과는 같고 왕복이 는다).

### 제안 2 — `recent_items_for_dedupe` 를 지문 비교로 · **대가 있음**

`backend/app/storage/repository.py:899`. 회차마다 최근 300건의 원본+이력+공지를 통째로
읽는다(1,767,765 B). 본문을 뺀 같은 조회는 96,895 B 다. 즉 이 조회의 **94%가 본문**이다.

다만 여기서는 본문이 실제로 쓰인다. `collect.py:555`가 `body_text` 로 지문을,
`collect.py:557`이 `body_html` 로 포스터 열쇠를 만든다. 그러니 그냥 뺄 수는 없다.

**방법 (가) 서버에서 지문만 받아 온다.** `body_text` 대신 `md5(body_text)` 를 select 해
먼저 지문으로 묶고, 지문이 같은 짝에 대해서만 본문을 읽는다. 자동 병합의 필요 조건이
본문 지문 일치라는 것은 이미 `run_dedupe_backfill` 의 주석이 근거로 삼고 있는 성질이다
(계획 9.1절). **병합 결과는 같다.**
- **대가:** 포스터 열쇠(`body_html` 을 파싱해 그림 주소를 뽑는다)는 서버에서 만들 수
  없다. 포스터 묶음에서 나오던 **`review` 판정을 놓친다.** 그 묶음은 원래 병합을
  만들지 않으므로 공개 결과는 달라지지 않지만, 사람이 볼 검토 후보가 줄어든다.
  포스터 열쇠를 유지하려면 `body_html` 은 계속 읽어야 하고, 그러면 절감은 절반 아래다.

**방법 (나) 지난 회차 이후 새로 관측된 것만 대상으로 한다.** 지금은 회차마다 같은
300건을 다시 읽는다. 기준 회차의 신규+갱신은 55건뿐이었다.
- **대가:** 새 글끼리만 비교하게 되어, 새 글과 **기존** 글의 중복을 놓친다. 이건
  중복 판정의 목적 자체를 깎는 것이라 권하지 않는다. 굳이 한다면 「새로 관측된 것 ×
  최근 300건」의 한쪽만 새 것으로 두는 형태여야 하고, 그러면 300건은 여전히 읽어야 한다.

**권하는 순서:** 제안 1을 먼저 적용하고, 그것으로 예산이 맞으면 제안 2는 두는 편이 낫다.
예산이 더 필요할 때 (가)를 검토하되 포스터 검토 후보가 줄어드는 것을 감수할지 정한다.

## 확인하지 못한 것

- **실제 전선 바이트.** 위 숫자는 `octet_length(row::text)` 근사치다. Supabase 가 무엇을
  egress 로 계량하는지(프로토콜·TLS·연결 오버헤드 포함 여부)는 확인하지 못했다.
  같은 회차의 본문 원바이트(11.36 MB)와 문자열화 바이트(12.83 MB) 차이가 13% 였으므로
  오차는 그 정도 규모로 본다.
- **`pg_dump` 원본 125MB.** 사용자가 알려준 값이고 데이터베이스 크기 188MB 와 어긋나지
  않지만, 이번에 직접 덤프를 뜨지는 않았다(그 자체가 125MB egress 다).
- **저장소 변수 `KHU_SOURCE_CONCURRENCY`, `KHU_INITIAL_UNTIL` 의 현재 값.** 읽지 않았다.
  감시의 데이터베이스 읽기는 값과 무관하게 무시할 수준이다.
- **`--prune` 을 실제로 돌려 본 것은 아니다.** R2 백업 목록(11개)은 읽었고, 거기에
  보존 규칙을 그대로 적용해 계산했다.
- **내보내기(`export/static.py`)의 읽기량.** 다른 작업이 같은 시간에 그 파일을 증분
  방식으로 고치는 중이라 손대지 않았고 재지도 않았다. 예산 표에는 그쪽 목표치
  (회차당 2~3MB)를 그대로 넣었다.
- **목록에 오른 글 수의 정확한 대응.** `preload_listing_items` 는 목록에 오른 5,845건을
  모두 조회하지만 데이터베이스에 있는 것만 행을 돌려준다. 「출처별 `list_items` 만큼
  최근에 본 원본」으로 근사해 3,936행을 얻었고, 「최근 150분 안에 다시 본 원본」이라는
  다른 방법으로도 3,697행 / 12.32 MB 가 나와 서로 맞았다. 둘 다 근사다.
