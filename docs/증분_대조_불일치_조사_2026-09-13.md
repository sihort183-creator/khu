# 증분·전체 대조 불일치 조사 (2026-09-13)

## 한 줄

증분이 바뀐 것을 놓친 것이 아니다. **자료는 같고 배열의 차례만 달랐다.** 공지 하나가

## 2. 무엇이 어떻게 달랐나

R2 에서 최신 개정(`r1789270095-ef4effc0`, 전체 방식으로 공개된 것)과 그 앞 개정
(`r1789265903-41ef0a15`)의 같은 파일을 받아 필드 단위로 견주었다. 개정 명세의 값이 곧
내용 해시라, 명세를 맞춰 보는 것이 파일을 바이트로 맞춰 보는 것과 같다.

### 2.1 상세 3개 — `sources[]` 의 차례만 뒤바뀜

`ntc-318c1a7ed0ed`, `ntc-91a0eb5fa95a`, `ntc-b0fb0c097eff` 셋 다 **원소가 같고 차례만
다르다.** 빠지거나 더해진 원문은 없다. 예를 들어 `ntc-b0fb0c097eff`:

| 자리 | 이전 개정 | 최신 개정 |
|---|---|---|
| `sources[0]` | 경희대학교 대학생활 (`item-22b652bacc5c`, 대표) | 앵커사업단 (국제캠퍼스) 커뮤니티 (`item-b73e0b7b62a1`) |
| `sources[1]` | 앵커사업단 (국제캠퍼스) 커뮤니티 (`item-b73e0b7b62a1`) | 경희대학교 대학생활 (`item-22b652bacc5c`, 대표) |

`ntc-91a0eb5fa95a` 는 활성 원문이 6개인데 그중 넷이 자리를 맞바꿨다. `is_primary` 가

이 셋은 **증분 회차에서 물려받은(reused) 공지**다. 확인:

| 공지 | DB `updated_at` / 현재 개정 | 이전 판 기록의 `u` / `r` | 증분에서 |
|---|---|---|---|
| `ntc-318c1a7ed0ed` | `2026-09-09T09:36:35.849407Z` / `rev-bbaad5a30828` | 같음 | 물려받음 |
| `ntc-91a0eb5fa95a` | `2026-09-12T04:24:13.909285Z` / `rev-e56307624c8b` | 같음 | 물려받음 |
| `ntc-b0fb0c097eff` | `2026-09-09T16:14:51.659005Z` / `rev-7a71ed19fc37` | 같음 | 물려받음 |

즉 증분은 이전 개정의 상세 파일을 그대로 물려받았는데, **전체 회차가 같은 자료로 다른
차례의 파일을 새로 만들어** 둘이 어긋났다. 물려받은 쪽이 틀린 것이 아니다.

### 2.2 상세 1개 + 목록 1쪽 — `secondary_categories` 의 차례

`ntc-3071cf54451e`(「★정경대학 공통 공지 관련 안내사항★」)는 최신 개정과 이전 개정의
**해시가 같다.** 그런데도 어긋났다는 것은, 이 공지는 물려받은 것이 아니라 그림자
회차가 **다시 만들었고**, 그 결과가 전체 회차의 결과와 달랐다는 뜻이다.

이 공지는 원문 발행일이 `2026-12-31`(미래)이라 보이는 날짜가 「처음 본 시각」으로 바뀐다
(`published_adjusted = true`). 그런 공지는 시간이 지나면 보이는 날짜가 저절로 달라지므로
증분이 **회차마다 반드시 다시 읽는다**(`state.py` 의 `NoticeState.adjusted`).

운영 DB 의 실제 줄:

```
ctid        category_code   is_primary
(401,77)    career          True
(401,78)    graduation      False
(401,79)    academic        False
```

두 길로 읽어 보면 차례가 갈린다(운영 DB 에서 직접 확인):

```
색인 훑기(Index Scan, 증분이 타는 길)   academic, career, graduation  -> 나머지 = [학사, 졸업]
차례 훑기(Seq Scan,  전체가 타는 길)    career, graduation, academic  -> 나머지 = [졸업, 학사]
```

공개된 파일(전체 방식)은 `["graduation", "academic"]`, 그림자(증분)는
`["academic", "graduation"]`. 목록 항목이 달라졌으니 이 공지가 실린 **`page/21.json`
까지 함께** 어긋났다. 공지 하나가 파일 둘을 어긋나게 한다.

`page/21.json` 의 50개 항목을 이전 판 기록의 항목과 하나씩 맞춰 보니 **전부 일치**했다.
쪽 경계가 밀린 것도, 다른 공지가 끼어든 것도 아니다. 오직 이 공지의 주제 배열뿐이다.

## 3. 원인

`backend/app/export/static.py` 에서 공지가 들고 있는 줄을 읽는 조회에 `ORDER BY` 가
없었다. 파이썬은 조회가 돌려준 차례를 그대로 배열에 담는다.

```python
categories_query = select(m.NoticeCategory)                  # ORDER BY 없음
audiences_query  = select(m.NoticeAudience, ...)             # ORDER BY 없음
_linked_sources_query()                                      # ORDER BY 없음
select(m.Attachment).where(...in_(revision_ids))             # ORDER BY 없음
select(m.NoticeContactMention).where(...in_(revision_ids))   # ORDER BY 없음
```

SQL 은 `ORDER BY` 가 없으면 차례를 약속하지 않는다. 그래서 차례를 실행 계획이 정했고,
**두 방식은 서로 다른 계획을 부른다.**

```
전체 회차  공지를 전부 읽으니 조건이 없다   -> Seq Scan      -> 물리적(ctid) 차례
증분 회차  바뀐 공지만 고른다(IN 목록)      -> Index Scan    -> 색인 키 차례
```

운영 DB 의 `EXPLAIN` 으로 직접 확인했다.

```
좁은 IN :  Index Scan using uq_notice_categories_notice_id_category_code on notice_categories
전체    :  Seq Scan on notice_categories  (rows=31774)
```

`uq_notice_categories_notice_id_category_code` 는 `(notice_id, category_code)` 색인이라
색인 훑기는 **코드 사전순**을 내놓고, 차례 훑기는 **넣은 순서**를 내놓는다. 둘이 같을
이유가 없다.

### 왜 전체 회차끼리도 갈라졌나 (`sources[]`)

`sources[]` 를 만드는 조회는 전체 회차에서 이런 계획으로 돈다.

```
Hash Left Join
  -> Hash Join
       -> Seq Scan on notice_sources ns (Filter: is_active)
       -> Hash -> Seq Scan on source_items si
  -> Hash -> Seq Scan on source_item_revisions r
```

**확인한 것**: 전체 방식으로 만든 두 개정(`...41ef0a15`, `...ef4effc0`)이 자료가 하나도
바뀌지 않은 공지에 대해 서로 다른 `sources[]` 차례를 내놓았다. 그리고 좁은 IN 으로 읽은
차례는 `ctid` 차례와 같았고, 그것이 이전 개정의 차례와 같았다.

**추론(직접 재지는 못했다)**: 작업 메모리가 2MB 라 해시 결합이 여러 판(batch)으로 쪼개져
디스크로 넘어가면 결과가 나오는 차례가 회차마다 달라질 수 있다. 위 관찰과 맞아떨어지지만,
`EXPLAIN (ANALYZE, BUFFERS)` 로 판 수를 재지는 않았다. 운영 DB 가 지금 디스크 입출력
한도 경고 상태라 무거운 조회를 돌리지 않았다.

원인을 「해시 결합의 판 쪼개기」로 못 박지 않아도 고치는 방법은 같다. **차례를 약속하지
않는 조회에 차례를 기대고 있었던 것**이 문제다.

### 후보였지만 아니었던 것

처음에 의심한 것들은 모두 **아니었다**. 실제 DB 행으로 확인했다.

| 후보 | 결과 |
|---|---|
| 트리거가 못 잡은 변경(병합으로 `source_count` 가 바뀜 등) | 아니다. 네 공지 모두 `updated_at`·현재 개정 id 가 이전 판 기록과 정확히 같았고, `source_count` 도 같았다 |
| 발행일 미래→현재 전환을 놓침 | 아니다. `adjusted` 인 공지는 계획이 늘 다시 읽도록 되어 있고 실제로 그렇게 돌았다 |
| 상태 기록의 목록 항목이 낡음 | 아니다. `page/21.json` 의 50개 항목이 기록과 전부 일치했다 |
| 조직·캠퍼스 이름, 중계 주소 변경 | 아니다. 그런 변경은 지문(fingerprint)이 바뀌어 전체 방식으로 돌게 되어 있다 |
| 비교 시점 차이(신선도 등) | 아니다. 두 방식이 같은 세션·같은 `now` 로 돌고, 신선도는 내용 객체에서 빠져 개정 명세로 간다 |

### 트리거(0004)는 무죄

`0004_notice_touch_triggers` 가 놓친 변경 경로는 이번 건에 없다. 어긋난 네 공지는
**자료가 하나도 바뀌지 않았다.** 바뀌지 않은 것을 트리거가 잡을 일은 없다. 이번 수정은
트리거를 건드리지 않으므로 **새 마이그레이션(0005)은 만들지 않았다.**

## 4. 수정

차례를 데이터베이스에 맡기지 않고, 읽어 온 뒤 파이썬에서 배열마다 못 박는다.
`ORDER BY` 로 데이터베이스에 시키지 않은 이유는 수만 행 정렬이 작업 메모리(2MB)를 넘겨
임시 파일을 만들기 때문이다. 공지 하나가 들고 있는 줄은 몇 개뿐이라 파이썬에서 세우는
값은 사실상 공짜다.

### `backend/app/export/static.py`

새 차례표와 두 개의 열쇠 함수를 더했다.

```python
CATEGORY_ORDER  = {code: index for index, code in enumerate(CATEGORY_LABELS)}
AUDIENCE_ORDER  = {"organization": 0, "campus": 1, "university": 2, "undetermined": 3}
```

| 배열 | 새 차례 | 고친 곳 |
|---|---|---|
| `secondary_categories` | 대표가 먼저, 나머지는 사전(`CATEGORY_LABELS`) 차례. 모르는 코드는 맨 뒤 | `_build_notice` |
| `audiences` | 조직 → 캠퍼스 → 전체 → 미정, 같으면 식별자 | `_build_notice` |
| `sources[]` | 대표 원문이 맨 앞, 나머지는 출처 이름, 같으면 원문 식별자 | `_notice_detail` |
| `attachments` | 파일 이름, 같으면 식별자 | `_notice_detail` |
| `contact_mentions` | 원문 글자, 같으면 식별자 | `_notice_detail` |

대상의 차례를 이름이 아니라 **식별자**로 세운 이유는, 조직 이름이 바뀌어도 차례가 흔들리지
않게 하기 위해서다.

같은 종류의 흔들림을 덤으로 정리했다. 이쪽은 어느 방식이든 매 회차 전부 다시 읽으므로
증분·전체가 어긋나지는 않지만, 차례가 흔들리면 **내용이 같은데도 회차마다 새 객체를
올리게 된다**(R2 쓰기 낭비).

- 연락처의 `channels`(우선순위가 같을 때), `campuses`, `evidence`
- 연락처 목록 자체 — 조직 이름·서비스 이름이 같을 때 식별자로 가른다. 이 차례가 연락처
  목록의 **쪽 경계**도 정한다
- 조직의 `campuses`
- `ORDER BY` 에 동점 가르개 추가 — `Organization.name → .id`, `Source.name → .id`,
  `Campus.name → .id` (작은 표라 정렬 비용이 문제되지 않는다)

### `backend/app/export/state.py`

```python
EXPORT_FORMAT_VERSION = "2"   # 1 -> 2
```

이전 판 기록에 담긴 목록 항목은 **옛 차례**로 만들어져 있다. 그대로 물려받으면 새 차례로
만든 항목과 한 목록에 섞인다. 이 값을 올리면 지문이 달라져 배포 뒤 **한 회차만 전체로**
돌고, 그때 모든 파일이 새 차례로 다시 만들어진다.

### 바꾸지 않은 것

- 운영 DB (쓰기 없음)
- 마이그레이션 (0005 만들지 않음 — 트리거 문제가 아니다)
- 저장소 변수 `KHU_EXPORT_MODE` (여전히 `shadow`)
- 커밋·푸시·배포 (하지 않음)

하나도 건드리지 않았다. 위 386개는 그 수정까지 함께 있는 상태에서 돈 결과다.

**다만 겹칠 자리가 하나 있다.** 저쪽의 `tests/test_export_order.py` 도 「목록 순서는
파이썬이 정한다」를 다룬다. 다루는 대상은 다르다.

- 저쪽 — **공지 목록 전체의 순서**. 쓰이지도 않는 정렬을 데이터베이스에 시키지 않으려고
  `_load_notices` 의 큰 조회에서 `ORDER BY` 를 걷어내는 쪽이다.
- 이쪽 — **공지 하나가 들고 있는 배열의 차례**(주제·대상·원문·첨부·문의처).

지금 시점에 둘을 함께 돌리면 81개가 모두 통과한다. 하지만 저쪽이 앞으로
`backend/app/export/static.py` 를 고치면 이 수정 위에 겹쳐 쓰게 된다. 합칠 때 서로의
`static.py` 변경을 확인하는 편이 좋다.

## 6. 나흘 추이

`gh run download <id> -n selfcheck` 로 09-10 ~ 09-13 의 성공 회차 **99개**를 받아
`export_consistency` 를 모았다.

| 날짜(KST) | 회차 | 어긋남 0 | 최소 | 중앙 | 최대 | `3071` 이 낀 회차 | 파일 빠짐·더함 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 2026-09-10 | 18 | **0** | 2 | 3 | 14 | 15 | 0 |
| 2026-09-11 | 29 | **0** | 2 | 2 | 10 | 27 | 0 |
| 2026-09-12 | 29 | **0** | 2 | 3 | 9 | 29 | 0 |
| 2026-09-13 | 23 | **0** | 2 | 2 | 6 | 23 | 0 |
| **합계** | **99** | **0** | 2 | 3 | 14 | 94 | 0 |

읽는 법.

- **99개 회차 가운데 어긋남이 0 인 회차는 하나도 없다.** 이번 회차만의 일이 아니라 나흘
  내내 이어진 상태다. 자체 점검이 나흘째 「이상」이었던 것이 그대로 사실이다.
- **바닥이 2다.** `ntc-3071cf54451e` 하나가 99회차 중 94회차에 끼어 있다. 미래 발행일이라
  회차마다 다시 읽히고, 주제가 둘이라 매번 차례가 갈린다. 이 공지가 상세와 목록 한 쪽,
  합쳐 2개를 고정으로 만들어 냈다.
- **나머지는 들쭉날쭉하다.** 회차마다 2~14개 사이를 오간다. 전체 회차의 해시 결합 차례가
  흔들리는 만큼 `sources[]` 가 걸려든다. 특정 공지에 매인 것이 아니라, 예시에 한 번이라도
  나온 공지 파일이 98개다(예시는 회차당 최대 10개까지만 실리므로 실제는 더 많다).
- **파일이 빠지거나 더 생긴 적은 한 번도 없다.** 99회차 모두 0. 증분이 만드는 파일 **목록**은
  줄곧 정확했다.

흔들릴 수 있는 공지가 얼마나 되는지도 셌다(운영 DB, 보이는 공지 25,142건 기준).

| | 건수 |
|---|---:|
| 나머지 주제가 2개 이상 | 1,297 |
| 대상이 2개 이상 | 2,099 |
| 활성 원문이 2개 이상 | 666 |
| 첨부가 2개 이상인 개정 | 578 |
| 문의처가 2개 이상인 개정 | 0 |

이 정도가 「차례가 갈릴 수 있는」 모집단이다. 회차마다 그중 몇 건만 실제로 갈린 것은 두
계획이 대개 우연히 같은 차례를 내놓기 때문이지, 안전해서가 아니다.

## 7. 증분으로 전환해도 되나

**고친 코드를 배포하고, 그림자 대조가 0 인 회차를 며칠 보고 나서 전환하면 된다.
지금 당장은 아니다.**

전환해도 된다고 보는 근거:

- 어긋남의 정체가 밝혀졌고, **자료가 틀린 적은 없다.** 다섯 파일 모두 원소가 같고 차례만
  달랐다. 증분이 변경을 놓친 사례는 99회차 어디에도 없었다.
- 파일 목록은 99회차 내내 정확했다(빠짐·더함 0). 증분의 계획 판정 자체는 건강하다.
- 물려받은 쪽이 오히려 안정적이었다. `sources[]` 세 건은 **전체 회차가** 회차마다 차례를
  흔든 것이고, 증분은 이전 판을 그대로 물려받아 흔들리지 않았다.
- 트리거(0004)가 놓친 경로는 이번 조사에서 발견되지 않았다.

지금 당장은 아니라고 보는 근거:

- 고친 코드가 아직 **배포되지 않았다.** 지금 전환하면 옛 차례로 만든 이전 판 항목을 그대로
  물려받아 차례가 뒤섞인다.
- `EXPORT_FORMAT_VERSION` 을 올렸으므로 배포 뒤 **첫 회차는 전체로 돈다.** 그 회차가
  기준선을 새로 세운다. 전환 판단은 그다음부터의 그림자 대조를 보고 해야 한다.
- 「어긋남 0」을 실제로 본 적이 아직 한 번도 없다. **0 이 나오는 것을 눈으로 확인하는 것**이
  전환의 최소 조건이다.

권하는 차례:

1. 이 수정을 배포한다(커밋·푸시는 사용자 몫).
2. 다음 회차가 전체로 도는지, 그 회차의 그림자 대조가 **0** 인지 본다.
3. `shadow` 로 하루쯤(24회차) 더 두고 줄곧 0 인지 본다.
4. 그때 `KHU_EXPORT_MODE=incremental` 로 바꾼다. 증분으로 바꾼 뒤에도 하루 한 번 전체
   재생성이 돌고 그 회차가 곧 대조 점검이 되므로, 어긋나면 다시 드러난다.

## 8. 확인하지 못한 것

정직하게 적어 둔다.

- **해시 결합이 판을 쪼개서 차례가 흔들렸다는 것**은 추론이다. 전체 회차끼리 차례가 갈린
  것은 두 개정을 받아 직접 확인했지만, `EXPLAIN (ANALYZE, BUFFERS)` 로 해시 결합이 실제로
  몇 판으로 쪼개졌는지까지 재지는 않았다. 운영 DB 가 디스크 입출력 한도 경고 상태라 무거운
  조회를 피했다.
- **09-10 이전 회차**는 받아 보지 않았다. 증분화가 들어간 09-09부터 09-10 09:13 사이에
  어긋남이 있었는지는 모른다. 구조상 처음부터 있었을 것으로 보이지만 확인하지 않았다.
- **그림자 회차가 실제로 만든 파일의 바이트**는 저장되지 않으므로 직접 받아 보지 못했다.
  물려받는 공지는 「이전 개정의 객체와 같다」는 성질로, 다시 읽는 공지는 운영 DB 에서 두
  실행 계획을 각각 돌려 재현하는 것으로 갈음했다. 두 방법 모두 관찰한 해시와 맞았다.
- **회차마다 몇 건이 갈렸는지의 전체 목록**은 모른다. 자체 점검의 `examples` 가 회차당
  최대 10개까지만 싣기 때문이다. 어긋난 **개수**는 전부 정확하다.
- 첨부·문의처의 차례가 운영에서 실제로 갈린 것을 **관찰하지는 못했다.** 어긋난 네 공지는
  첨부도 문의처도 0건이었다. 같은 구조의 조회라 함께 고쳤다(첨부가 2개 이상인 개정이
  578건 있다).
- 조직·연락처 쪽 차례 흔들림이 실제 R2 쓰기 낭비로 이어졌는지 **재지 않았다.** 조사한 두
  개정 사이에서는 `organizations.json` 이 흔들리지 않았다.
