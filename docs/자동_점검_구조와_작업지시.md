# 자동 점검 구조와 작업 지시서

이 문서는 **다른 세션이 그대로 집어 들고 실행하도록** 쓴다. 사용자는 코드를 읽지 않는다.
사용자에게 오류·누락을 직접 찾아오게 하지 않는다. 찾는 일은 기계와 담당 세션이 한다.

작성 시점: 2026-09-07 00:30 KST. 아래 수치는 모두 이 시점에 운영 DB·원문으로 직접 확인한 값이다.
수집이 계속 돌고 있으므로 수치는 변한다. **문서의 수치를 현재 상태로 인용하지 말고 재조회한다.**

## 2. 자동화 구조 — 무엇이 사람 없이 돌고, 무엇이 안 도는가

솔직하게 나눈다. 과장하지 않는다.

### 2.1 사람 없이 도는 것 (GitHub Actions)

사용자 컴퓨터가 꺼져 있어도 돈다. 지금도 돌고 있다.

- `.github/workflows/collect.yml` — 수집. 유지 수집은 매시 17분, 초기 수집은 `app.run.initial`이
  회차 종료 시 `초기 작업 이어받기` 단계에서 스스로 다음 회차를 dispatch 하여 연속 실행한다.
- 회차 1회는 약 5분, 출처 약 50개, 신규 약 400건 규모다(2026-09-07 실측).
- **여기에 자체 점검 단계를 붙인다.** 규칙 기반이라 LLM 없이 확정적으로 돈다. → 4절.

### 2.2 세션이 있어야 하는 것

- 코드 수정, 원인 규명, 판단이 필요한 분류.
- 클로드 서브에이전트는 세션 안에서만 산다. **"자는 동안 클로드가 알아서 고쳐 놓기"는 현재 구조로 불가능하다.**
  담당 세션은 이것을 할 수 있다고 사용자에게 말하지 않는다.

### 2.3 그래서 실제로 굴러가는 모양

```
밤:   Actions 가 수집 + 자체 점검  →  이상 목록을 산출물로 남긴다 (사람 개입 0)
아침: 세션이 그 목록만 읽고 원인 규명·수정  →  사용자에게 결과 한 장 보고
```

사용자가 게시판을 뒤져 오류를 찾아올 필요는 없다. 4절의 점검이 대신 찾는다.

## 3. 지금까지 확인된 사실 (근거 포함)

### 3.1 조회 방법

`backend/.env` 에 운영 `KHU_DATABASE_URL` 이 있다. 읽기 전용 조회는 아래로 한다.

```bash
cd backend && .venv/Scripts/python.exe -c "
import sys; sys.stdout.reconfigure(encoding='utf-8')
from sqlalchemy import text
from app.config import settings
from app.storage.db import session_scope
with session_scope(settings) as s:
    print(s.execute(text('select count(*) from notices')).all())
"
```

Windows 콘솔은 한글이 깨지므로 `sys.stdout.reconfigure(encoding='utf-8')` 를 반드시 넣는다.

### 3.2 확인된 상태 (2026-09-07 00:30 KST)

- 활성 출처 370개. 공지 5,254건, 원문 4,866건 이상(증가 중).
- **날짜 경계는 운영에 미적용.** `date_ordered=true` 설정 0개, `scan_stop_reason='date_boundary'` 기록 0건.

### 3.3 "게시판 통째 누락"의 실체 — 대부분 누락이 아니다

원문 0건 출처를 6곳 직접 접속해 확인했다. 전부 HTTP 200, 파서도 10~11건 정상 인식했다.
0건이 된 이유는 **그 게시판의 최신 글조차 2026-03-01 보다 오래되어서**였다.
기간 밖 글은 저장하지 않는다([`backend/app/run/collect.py`](../backend/app/run/collect.py) 의 과거 재개 주석 참조).

| 게시판 | 파서 인식 | 최신 글 |
| --- | --- | --- |
| 화학과 게시판 | 10건 정상 | 2025-11-12 |
| 공과대학 대학생활 | 10건 정상 | 2025-02-12 |
| 일본어학과 공지사항 | 10건 정상 | 2024-12-02 |
| 규제과학과 공지사항 | 10건 정상 | 2025-09-08 |
| 연구처 과제공고 | 10건 정상 | 2026-02-03 |
| **원자력공학과 게시판** | 11건 정상 | **2026-09-02** ← 설명되지 않음 |

3월 이전을 자르기로 했으므로 앞의 5곳은 **올릴 것이 없는 게시판**이다. 누락으로 세지 않는다.
**원자력공학과만 실제 조사 대상이다.** 기간 안 글이 있는데 저장이 0건이다.

### 3.4 "일부만 수집"의 실체 — 종료 사유만 보고 판단하면 틀린다

`last_scan_stop_reason` 만 보면 과대 계상된다. **`backfill_oldest_date` 를 2026-03-01 과 대조해야** 실제 범위 확보 여부를 안다.
2026-09-07 00:20 기준 활성 370개:

| 종료 사유 | 출처 | 3월 이전까지 내려감(범위 확보) | 아직 3월에 못 닿음 |
| --- | --- | --- | --- |
| `page_limit` | 64 | **63** | 1 |
| `end_of_board` | 75 | 64 | 6 |
| `time_budget` | 123 | 9 | **103** |
| `in_progress` | 8 | 1 | 6 |
| `list_error` | 2 | 0 | 0 |
| 기록 없음 | 98 | 0 | 0 |

- `page_limit` 63개는 문제 아님 — 3월 이후는 이미 다 확보했고 못 본 건 아주 오래된 과거뿐이다. 자를 구간이다.
- `end_of_board` 중 3월에 못 닿은 6개도 정상 — 게시판에 3월보다 오래된 글이 아예 없다.
- **실제 미완은 `time_budget` 103개.** 여기에 미시작분이 더해진다. 수집을 계속 돌리면 줄어든다.

이전 보고에서 "뒤쪽 못 본 167개"라고 쓴 것은 틀렸다. 같은 실수를 반복하지 않는다.

## 4. 자체 점검 단계 — 이것을 만든다

`collect.yml` 의 수집 실행 뒤에 점검 단계를 추가한다. 규칙 기반이며 LLM을 쓰지 않는다.
결과는 산출물로 업로드하고, 이상이 있으면 `$GITHUB_STEP_SUMMARY` 에 요약을 남긴다.
**점검이 실패해도 수집을 실패시키지 않는다**(`continue-on-error`). 수집을 막지 않는 것이 최우선이다.

구현 위치 제안: `backend/app/ops/selfcheck.py`, 실행은 `python -m app.ops.selfcheck`.

검출 항목:

| # | 이름 | 규칙 | 왜 |
| --- | --- | --- | --- |
| 1 | 조용한 0건 | 목록 조회는 성공(`last_list_success_at` 있음)했는데 원문 0건인 출처. **원문 1페이지를 실제로 받아** 파서 인식 건수와 최신 글 날짜를 함께 기록한다. 최신 글이 2026-03-01 이후인데 0건이면 **이상**, 그 이전이면 **범위 밖(정상)** 으로 분류. | 3.3의 원자력공학과 같은 케이스를 사람이 찾지 않아도 잡는다. 상태 코드만으로는 절대 구분되지 않는다. |
| 2 | 범위 미달 | `backfill_oldest_date > 2026-03-01` 인 출처 수와 목록. 회차마다 이 수가 줄고 있는지 추세를 남긴다. | 3.4. 줄지 않으면 수집이 헛돌고 있다는 신호다. |
| 3 | 날짜 오염 | 발행일이 미래이거나 1990년 이전인 공지. | 2099-12-31 같은 값. |
| 4 | 상세 실패 | `last_detail_error` 가 있는 원문 수, 오류 메시지 상위 유형별 집계. 비공개·로그인 필요와 추출 실패를 메시지로 구분 시도. | 231건이 쌓여 있고 성격이 구분되지 않았다. |
| 5 | 접근 실패 | `consecutive_failures > 0` 출처와 `last_error_kind`. 3회 이상 연속 실패는 별도 강조. | timeout·connection 은 재시도로 풀리지만 고착되면 사람이 봐야 한다. |
| 6 | 좀비 실행 | `finished_at is null` 이면서 시작 후 6시간 지난 `runs`. | KNOWN_ISSUES 20번. |
| 7 | 공개 지연 | 최신 공개 개정 생성 시각이 마지막 수집 종료보다 오래됐는지. | 모았는데 공개가 안 나가는 상태를 잡는다. |

출력 형식: `backend/.localstore/selfcheck.json` (기계 판독용) + 요약 표(사람 판독용).
1번은 원문 요청이 필요하므로 대상이 많을 때는 회차당 상한(예: 30곳)을 두고 순환한다.

## 5. 실행 순서

담당 세션은 아래를 순서대로 하고, 중간에 사용자에게 판단을 넘기지 않는다.
막히면 그 항목만 남기고 나머지를 끝낸 뒤 무엇을 왜 못했는지 명시한다.

1. **수집이 돌고 있는지 먼저 확인.** `gh run list -L 3`. 멈춰 있으면 `collect.yml` 을 dispatch 해서 먼저 살린다.
   다른 어떤 작업도 수집을 대기시키지 않는다.
2. ~~3월 이전·미래 날짜 공개 차단.~~ **2026-09-07 완료.** 발행일 불명까지 함께 막았다.
   남은 것은 발행일 불명 566건의 원인 조사다(추출 실패인지 원문에 날짜가 없는지).
3. **자체 점검 구현·배치** (4절). 완료 판정: 수집 회차가 끝난 뒤 산출물에 7개 항목이 모두 채워진다.
4. **원자력공학과 원인 규명** (3.3). 완료 판정: 0건인 이유를 원문 근거로 설명하고, 버그면 고쳐 저장된 것을 확인한다.
5. **결과 보고 한 장.** 수집 진척(범위 미달 출처 수 추세), 공개 건수, 점검 검출 목록, 남은 것.

### 손대지 말 것 / 먼저 물을 것

- **날짜 정렬 검증(`app.ops.date_order`)을 다시 돌리지 않는다.** 초기 수집이 끝나기 전에는 하지 않는다.
  `--max-pages` 기본값이 300 이라 매우 오래 걸리고, `apply` 는 통과 출처의 `backfill_cursor_page` 를 1로 되감아
  이미 끝난 수집을 다시 시키게 된다. 이것 때문에 2026-09-06 수집이 멈췄다.
- 공지 아닌 글 필터링(KNOWN_ISSUES 8번)은 넣지 않기로 되어 있다. 바꾸려면 사용자에게 먼저 묻는다.
- 실행 취소·삭제 같은 되돌릴 수 없는 조작은 사용자 승인 없이 하지 않는다.

## 6. 남은 것 (이 문서 범위 밖이지만 잊지 말 것)

- **프런트엔드가 아직 어디에도 배포되어 있지 않다.** `NEXT_PUBLIC_API_BASE` 가 비어 있어
  지금 배포해도 가상 데이터로 뜬다([`frontend/src/lib/api.ts`](../frontend/src/lib/api.ts)). 배포 설정 자체가 없다.
  "크롤이 끝나고 도메인만 붙이면 서비스"가 아니다. 프런트 배포·실데이터 연결·화면 확인이 통째로 남아 있다.
- 조회 서버(Cloudflare Worker `khu-notice-api`)는 배포되어 동작 중이다.
- 변경 없는 공개 파일 재사용의 운영 실측(1분 미만 목표)은 아직 측정하지 못했다.
