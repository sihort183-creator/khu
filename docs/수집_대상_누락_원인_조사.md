## 1. 결론 먼저

**"공지 게시판 857개 중 383개만 수집한다"는 셈이 맞지 않는다.**
857 은 *게시판 주소*의 수이고, 그중 **394개가 같은 게시판을 여러 호스트에서 연 거울**이다.
거울을 합치면 실제 게시판은 **463개**이고, 여기에 미정에서 승격한 16개를 더한 **479개 전부가
등록부에 들어 있다.** 등록조차 안 된 공지 게시판은 **0개**다.

| 공지 판정 857개의 행방 | 개수 |
| --- | ---: |
| 같은 게시판의 거울이라 대표 하나로 합쳐짐 | 394 |
| 등록부 active → DB active (수집 중) | 367 |
| 등록부 active → DB **pending** (등록부와 DB 가 어긋남) | **46** |
| 등록부 pending → DB pending (판정 근거가 약해 대기) | 47 |
| 등록부 active → DB delayed (연속 실패, 자동 복구) | 3 |
| 합계 | 857 |

여기에 별도로 2026-09-07 미정에서 승격한 16개가 active 로 들어와, 수집 중 383 = 367 + 16 이다.

그러므로 밝혀야 할 것은 세 가지로 좁혀진다.

| 갈래 | 개수 | 원인 | 되살릴 수 있나 |
| --- | ---: | --- | --- |
| **A. 등록부는 active 인데 DB 가 pending** | **46** | 손으로 만든 옛 등록부(전부 pending)로 먼저 넣은 뒤, 조사로 다시 만든 등록부에서 active 가 되었으나 `sources sync` 가 **기존 행의 상태를 절대 고치지 않는다** | **된다.** 표본 5곳 전부 2026년 9월 글이 정상으로 읽혔다 |

## 2. `[확인 필요]` 는 상태와 관계가 없다

이름이 `[확인 필요] ...` 로 시작하는 것이 pending 에 많아 보이지만, 그것은 상태 표시가 아니다.

`scripts/build_registry.py:154` 에서 **조직 이름을 학교 사이트 명부에서도 페이지 제목에서도
못 찾았을 때** `[확인 필요] {호스트}` 라는 자리표시자를 쓴다. 출처 이름은 `조직 이름 + 게시판
이름` 이라서 그 자리표시자가 앞에 붙는다. 이름을 지어내지 않겠다는 규칙
(`docs/SOURCE_DISCOVERY.md` 5단계)의 결과다.

| 상태 | `[확인 필요]` 로 시작 | 전체 |
| --- | ---: | ---: |
| active | 12 | 383 |
| pending | 20 | 93 |
| retired | 5 | 21 |
| delayed | 2 | 3 |

active 에도 12개가 있다. **이름을 못 찾은 것과 수집하지 않는 것은 별개다.**
이름 못 찾은 조직은 10개다.

## 4. 갈래 B — 판정 근거가 약해 대기 중인 47개

원인은 설계대로다. `scripts/build_registry.py:203`:

**되살릴 수 있나:** 표본 5곳 전부 목록이 정상으로 읽혔다. 기술적으로는 넣을 수 있다.

- 16개(상위 메뉴가 공지) 중 `교육대학원(유아교육전공) 서울/국제캠퍼스`, `디지털콘텐츠학과 학생지원`,

  거울 병합 키를 호스트로 만들어서 합쳐지지 않았다. 같은 내용일 수 있으니 넣기 전에 확인해야 한다.

## 6. 표에 안 나오는 네 번째 누락 — 조사 단계에서 빠진 것

`board_profiles.json` 은 **조사가 실제로 연 게시판**만 담는다. 조사가 못 연 것은 애초에 857 에
들어오지 못했다. `discovered.json` 을 직접 세면 다음과 같다.

| 빠진 지점 | 규모 | 확인한 것 |
| --- | --- | --- |
| **첫 화면을 못 연 사이트 3곳** | `khsma`(정경대학) · `khmba`(경영대학원) · `khmc`(의학계열실습지원센터) | `discovered.json` 에 `home_status: 0, pages_fetched: 0`. 그런데 그 앞 단계 `hosts.json` 에서는 세 곳 모두 `status: 200` 이고 게시판 힌트가 8·6·3 이었다. **일시적 실패였고 아무도 다시 확인하지 않았다.** khsma 3곳은 이번에 직접 받아 살아 있음을 확인했다 |
| **페이지 예산(200쪽)에 걸린 호스트 13곳** | `bme` `ce` `dc` `ee` `globaleminence` `gskh` `impact` `kmc` `news` `ois` `sdgs` `swcon` `www` | 대기열에 69~231쪽이 남은 채 멈췄다. 몇 개를 더 놓쳤는지는 **모른다** |

| 휴면 판정 | 514 | 학기가 시작되면 되살아나는 것이 있을 수 있다. 확인하지 않았다 |

## 8. 경고할 것

1. **"백필이 안 끝난다"는 인식과 실측이 다르다.** 수집 중인 386곳 중 **360곳(93%)이 이미
   백필 완료**다. 남은 26곳(진행 중 17 · 상세 대기 9)은 2026-09-07 커밋 `b9dacb6`·`20e4894`
   에서 원인 넷을 찾아 고쳤다. 그러므로 "두 배로 늘린다"가 아니라 **"24% 늘린다"**가 맞다.
2. **다만 지금은 가속 설정으로 돌고 있다.** `KHU_HOST_GROUP_MODE=host`,
   `KHU_HTTP_DELAY_SECONDS=0.5`, `KHU_HTTP_CONCURRENCY=16`, `KHU_LIST_PAGE_LIMIT=5` 는 첫
   백필을 빨리 끝내려고 푼 값이고 `collect.yml` 주석에 "백필이 끝나면 되돌린다"고 적혀 있다.
   97곳을 한꺼번에 넣으면 **그 설정을 유지해야 하는 기간이 4~10시간 늘어난다.**
   학교 서버에 그만큼 더 부담이 간다.
3. **한꺼번에 넣지 말고 나누기를 권한다.** A(46) + C(4) = 50곳을 먼저 넣어 백필을 끝내고,
   B(47)는 성격을 하나씩 판단한 뒤 넣는 편이 안전하다. B 의 31개는 행사 게시판이라
   넣으면 공지 목록의 성격이 바뀐다.
4. **폐쇄 21개를 통째로 되살리면 안 된다.** 4개는 거울이라 되살리면 같은 공지를 두 번 수집한다.
   9개는 마지막 글이 2018~2023년인 휴면이다.
5. **왜 그렇게 두었는지가 DB 에 남아 있지 않다.** `sources.status_message` 가 pending 93·
   retired 21 전부 비어 있어서, 이 조사는 `audit_logs` 시각과 git 이력과 `board_profiles.json`
   을 맞춰 역추적해야 했다. 앞으로 상태를 바꿀 때는 `status_message` 에 사유를 남기는 편이 좋다.
6. **`sources sync` 는 기존 행의 상태를 절대 고치지 않는다.** 등록부에서 pending → active 로
   바꿔도 DB 에 반영되지 않는다. 46개가 그렇게 생겼다. 승격은 `sources promote KEY` 로
   따로 해야 한다.
