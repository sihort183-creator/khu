# 발행일 불명 원인 조사

- 작성일: 2026-09-07
- 기준 시각: 2026-09-07 01:09 KST (운영 DB 조회). 수집이 계속 돌고 있어 절대 건수는 변한다.
- 조회 범위: 읽기 전용. 운영 DB 에 쓰지 않았고 되살리는 이행도 실행하지 않았다.
- 배경: 2026-09-07 사용자 결정 "발행일을 모르는 공지는 공개하지 않는다"(`자동_점검_구조와_작업지시.md` 1절, 커밋 `e8b0ecd`).

## 1. 결론 먼저

공개에서 빠진 **694건 가운데 654건(94.2%)은 발행일을 알고 있다.**
빠진 까닭은 원문에 날짜가 없어서가 아니라 **공개 판정이 `published_at` 만 보기 때문**이다.

`published_at` 은 "시각까지 아는 글"에만 값이 들어간다. `app/domain/dates.py` 의 `parse_published`
는 날짜만 적힌 원문에 시각을 지어내지 않고 `at=None, precision="date"` 로 돌려준다(계약 4절 12항).
그 결과 날짜를 정확히 아는 글도 `published_at` 이 비어 있고, 지금 판정은 이를 "발행일 불명"과
구분하지 않는다.

발행일을 정말 모르는 글은 **40건**이며, 그 가운데 **34건은 상세 원문에 날짜가 있는데 우리가 못 읽은
것**(어댑터 결함)이고, **6건은 원문 자체에 쓸 수 있는 날짜가 없다.**

인 것(= 지금 공개에서 빠지는 것). 합계 694건.

## 3. A·B 를 만든 지점 — 판정이 보는 열이 틀렸다

`app/export/static.py` 의 `_load_notices` 안 `within_window` 가 `notice.published_at` 만 본다.

```python
published = as_utc(notice.published_at)
if published is None:
    return floor is None      # ← 날짜만 아는 글까지 여기로 떨어진다
```

`published_at` 이 비는 경우는 둘이다.

1. 발행일을 정말 모른다(`published_precision='unknown'`, `published_date is null`). 40건.
2. **날짜는 알고 시각만 모른다**(`published_precision='date'`). 654건.

2번은 설계대로다. `app/domain/dates.py` 는 시각을 지어내지 않는다. 화면은 이미 이 구분을 지키고 있다
(목록 정렬·표시가 `published_date` 를 쓰고, `published_precision === 'unknown'` 일 때만 "날짜 미확정"
으로 적는다). 내보내기의 범위 판정만 이 구분을 빠뜨렸다.

어댑터별로 보면 654건이 왜 이렇게 많은지가 보인다.

| 어댑터 | 현재 개정 | datetime | date | unknown |
| --- | ---: | ---: | ---: | ---: |
| `khu_board` | 5,947 | 5,768 | 178 | 1 |
| `gnuboard` | 498 | 0 | 459 | 39 |

그누보드 게시판은 목록 칸에 `26-09-04` 처럼 날짜만 적는다. 어댑터는 목록에서 날짜를 얻으면 상세의
`등록일 26-09-04 09:04` 을 쓰지 않으므로(`gnuboard.py` 의 `if written and not published_raw`)
그누보드 쪽은 전부 `date` 정밀도가 된다. **이것은 결함이 아니다.** 날짜는 맞다. 판정만 고치면 된다.

`published_raw` 값 자체는 깨끗하다. `date` 정밀도 654건에서 가장 많은 값은 `2026-09-01`,
`2026-08-27` 같은 정상 날짜다. **날짜 파서 결함으로 볼 근거는 찾지 못했다.** 값이 있는데 해석에
실패한 것은 F 의 2건뿐이고, 그 둘은 원문 값이 실제로 날짜가 아니다.

## 5. 수정안

`domain/dates.py` 의 원칙을 깬다. 판정 쪽만 고친다.

| 대학주보 | 5 | 2026-09-06, 2026-09-06 → 범위 안 |

표본으로만 미루면 **공개까지 늘어나는 것은 10건 안팎**으로 보인다. 정확한 수는 전량을 다시 받아 봐야
알 수 있고, 이번 조사에서는 대량 요청을 하지 않았다. 모르는 것은 모른다고 적는다.

반영 시점도 즉시가 아니다. `repository.py` 의 상세 재점검 간격이 발행일 불명 항목에서
`recheck_days`(기본 14일)이므로 코드만 배포하면 최대 14일에 걸쳐 나뉘어 반영된다. 빨리 보려면 해당
6개 출처만 강제 재점검해야 한다.

### 5.3 (하지 않기를 권함) `published_at` 을 `published_date` 로 채우는 이행

날짜만 아는 654건에 `00:00` 같은 시각을 넣으면 판정과 총계를 한 줄도 안 고치고 맞출 수 있다. 그러나
그것은 원문에 없는 시각을 만드는 일이고 `domain/dates.py` 와 계약 4절 12항이 명시적으로 금지한다.
목록 정렬이 실제와 달라지고 화면의 "시각까지 앎 / 날짜만 앎" 표시도 거짓이 된다. 권하지 않는다.

## 6. 밝히지 못한 것

- C·D 34건을 실제로 되찾았을 때 **공개까지 늘어나는 정확한 건수**. 표본 6건으로 어림만 했다.
- 그누보드 상세에는 시각이 있는데(`등록일 26-09-04 09:04`) 목록 날짜를 우선해서 `date` 정밀도로
  굳는 459건. 상세를 우선하면 `datetime` 으로 올릴 수 있으나 전 항목의 개정을 새로 만드는 일이라
  득실을 따로 따져야 한다. 이번 조사 범위 밖이다.
- 이 조사는 `notices` 에 묶인 공개 대상만 셌다. 아직 승격되지 않은 `source_items` 는 따로 세지 않았다.
- 수집이 진행 중이므로 모든 숫자는 2026-09-07 01:09 KST 한 시점의 값이다.

## 7. 재현 방법

`backend/.venv/Scripts/python.exe` 로 `backend/.env` 의 `KHU_DATABASE_URL` 에 붙어 아래를 조회한다.
`sys.stdout.reconfigure(encoding='utf-8')` 를 먼저 부른다.

```sql
select (now() at time zone 'Asia/Seoul')::date as kst_today,
  count(*) filter (where n.published_at is null) as hidden_now,
  count(*) filter (where n.published_at is null
    and n.published_date between date '2026-03-01' and (now() at time zone 'Asia/Seoul')::date) as recover_inwindow,
  count(*) filter (where n.published_at is null and n.published_date < date '2026-03-01') as too_old,
  count(*) filter (where n.published_at is null and n.published_date is null) as unknown
from notices n
join source_items i on i.id = n.primary_source_item_id
join sources s on s.id = i.source_id
where n.status = 'visible' and s.is_public;
```

불명 40건의 출처별 내역은 `source_item_revisions.published_precision = 'unknown'` 을
`source_items.current_revision_id` 로 조인해 `sources.name` 으로 묶으면 나온다.
