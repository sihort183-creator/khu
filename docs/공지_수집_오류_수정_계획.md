# 공지 수집 오류 수정 계획

- 작성일: 2026-09-06
- 문서 상태: 원래 수정 계획. 이후 로컬 코드 수정과 검증을 진행했으며, 항목별 실제 완료 범위는 [수정 검증 결과](공지_수집_수정_검증_결과.md)에 기록한다. 운영 복구·배포는 미수행이다.
- 대상: 2026-03-01 이후 공지 수집 미완료, 수집·공개 지연, 공지 누락 및 잘못된 삭제
- 조사 근거: 알려진 오류 문서, 기존 백엔드 계획, 현재 작업 폴더의 코드와 등록부
- 조사 한계: 운영 배포 버전, 운영 데이터베이스, 실제 공개 파일 및 화면을 이번 조사에서 대조하지 않았다. 운영 피해 건수와 성능 수치는 구현 전 기준 조사에서 확정한다.

## 1. 목표와 완료 범위

수집 대상으로 확정한 공개 게시판의 **2026-03-01 이후 공지와 기간 밖의 진행 중 고정 공지**를 모으고, 실행이 중단되어도 빠짐없이 이어받으며, 최신 공지가 과거 수집 때문에 밀리지 않게 한다. 저장된 공지가 목록·상세·검색·맞춤 화면까지 전달되는 것을 완료 범위로 삼는다.

다음 네 가지를 함께 해결한다.

1. 어디까지 모았는지 증명할 수 있는 과거 수집과 재개 절차
2. 불완전한 탐색 때문에 정상 공지를 삭제하지 않는 판정과 기존 피해 복구
3. 불필요한 상세 요청·저장·데이터베이스 왕복을 줄이는 처리 구조
4. 미등록·미지원 출처 및 공개·화면 경로에서 발생하는 누락

학교 전체 게시판을 모두 조사했다는 주장과, 등록된 대상 게시판의 수집을 완료했다는 주장을 구분한다. 접근 불가·미지원·판정 대기 출처는 완료 집계에서 숨기지 않고 별도 수치와 이유를 공개한다.

### 2.2 현재 등록부와 문서의 차이

현재 등록부 파일 기준으로 출처는 463개이며 활성 416개, 검토 대기 47개다. 판정 자료에는 공지 게시판 857개, 성격 미정 97개, 휴면 514개가 있다. 같은 게시판의 여러 주소를 합치므로 게시판 수와 최종 출처 수는 일치하지 않는다. 탐색 대기 메뉴가 남은 사이트는 13곳이다.

이 숫자는 **로컬 등록부의 현황**이다. 운영 데이터베이스의 수집 대상 수나 실제 수집 성공 수로 사용하지 않는다. 기존 출처는 등록부 동기화만으로 운영 상태가 덮어써지지 않으므로 별도 대조가 필요하다.

알려진 오류 문서의 다음 항목은 상태와 근거를 재정리해야 한다.

- 13·14번: 시간 제한 대응과 업로드 동시 처리는 있지만 근본적인 수집·내보내기 비용이 남아 있다.
- 15번: 시간 예산 중단 보호는 있으나 식별자 불일치와 다른 부분 탐색 종료가 남아 있다. 부분 해결로 재평가한다.
- 16~19번: 날짜 범위·완료 기록·기간 밖 고정 공지·범위 표시는 이번 구현의 핵심이다.
- 20번: 오래된 실행을 정리하는 코드는 이미 있다. 다만 30분 기준은 현재 워크플로 최대 120분과 맞지 않으며, 공개 상태 기록 순서도 별도 문제다.
- 문서에 적힌 25분 수집·40분 실행 제한과 달리 현재 워크플로는 수집 예산 40분·최대 실행 120분·30분 간격 예약이다. 주석과 실제 값도 일부 불일치한다.

기존 공지 순서는 최초 노출 시각을 기준으로 한다. 과거 수집으로 새로 발견한 오래된 글이 위로 올라올 수 있으므로 게시일 기준 보기와 현재 기본 정렬의 차이를 검증한다. 이번 수정을 이유로 기본 정렬 정책을 임의 변경하지 않으며, 기존 계약을 유지할지 게시일 보기를 추가할지는 실제 화면 검토 결과에 남긴다.

## 4. 반드시 지킬 공통 조건

1. 동일 출처·동일 원문 번호는 원본 하나로 수렴한다.
2. 시간·페이지 제한, 통신 실패, 추출 실패, 증분 탐색 종료는 게시물 삭제의 근거가 아니다.
3. 목표 날짜 도달과 상세 수집 완료는 구분한다. 해결되지 않은 누락이 있으면 전체 완료라고 표시하지 않는다.
4. 재개 지점은 해당 구간 저장이 확정된 뒤에만 전진한다. 중단 직전 작업을 반복해도 중복 공개되지 않는다.
5. 최신 공지 확인과 과거 채우기에 각각 실행 시간을 배정하고, 특정 출처가 무기한 밀리지 않게 한다.
6. 날짜가 없거나 정렬이 불명확한 글을 임의로 기간 밖이라고 판단하지 않는다.
7. 원문 재발견은 자동 삭제 상태를 복구하지만 운영자가 숨긴 상태와 중복 병합 상태를 덮어쓰지 않는다.
8. 새 공개 개정은 필요한 파일과 검산이 완료된 후에만 전환한다. 실패하면 기존 공개 개정을 유지한다.
9. 원문 목록·저장·공개·검색 사이 차이는 제외·병합·접근 불가 등의 근거로 설명할 수 있어야 한다.
10. 시작일·수집 도달 범위·최근 확인·실패 정보를 분리하며, 단순 실행 성공으로 수집 완전성을 대신하지 않는다.

## 5. 단계별 수정 계획

### 1단계 — 운영 기준 조사와 재현 자료 확보

**작업**

- 실제 배포 버전과 최근 실행의 코드 버전을 현재 코드와 대조한다.
- 운영 출처를 활성·대기·지연·차단·중지 등으로 나누고 등록부와 차이를 기록한다.
- 출처별 마지막 시도·목록 성공·상세 완료·공개 건수·원문 상태·날짜 범위·실행 시간을 읽기 전용으로 집계한다.
- 대표 게시판은 본부·학사·장학·취업·학과·저빈도·고정 공지 다수·두 기존 게시판 형식·미지원 사이트를 포함해 선정한다.
- 원문 목록과 상세를 근거로 정상 사례와 실패 사례를 보관한다. 민감한 자격 증명과 불필요한 개인정보는 진단 자료에 넣지 않는다.
- 원문 요청 대기·전송·추출·데이터베이스·원문 저장·중복 비교·내보내기·업로드 시간을 분리하는 측정 항목을 정한다.

**산출물**: 운영 기준 보고서, 출처별 차이 목록, 재현용 원문 표본, 단계별 성능 기준값.

**통과 기준**: 로컬 코드의 결함과 운영에서 확인된 피해를 구분하고, 각 누락 사례를 어느 단계에서 잃었는지 추적할 수 있다.

### 2단계 — 삭제 오판 차단과 기존 공지 복구

**구현**

- 발견 집합을 출처에 종속된 원문 번호로 통일하고 저장 항목의 원문 번호와 비교한다. 내부 식별자와 원문 번호가 혼용되지 않도록 함수 인수와 타입을 명확히 한다.
- 탐색 종료 이유를 기록한다. 전체 게시판 종료, 날짜 경계 도달, 기존 글 구간 도달, 페이지 제한, 시간 제한, 요청·추출 실패를 구별한다.
- 날짜 경계나 증분 구간 도달은 전체 게시판 탐색 완료가 아니다. 범위 밖의 기존 글에 미발견 횟수를 올리지 않는다.
- 자동 삭제 확정은 검증된 전체 탐색 또는 개별 원문 재확인 정책으로 제한한다. 차단·시간 초과·일시 오류를 삭제로 해석하지 않는다.
- 재발견 시 내용 변경과 무관하게 미발견 횟수·원문 상태·자동 삭제된 공개 상태를 함께 복구한다.
- 병합된 공지에 다른 유효 원문이 남아 있으면 공개를 유지하고, 대표 원문 교체 필요성까지 검사한다.

**기존 데이터 복구**

1. 변경 전 관련 원본·공지·연결·감사 상태와 공개 개정을 보존한다.
2. 삭제 표시 항목과 상태 불일치 항목을 후보로 추출한다.
3. 원문 재확인 결과에 따라 복구 가능·실제 삭제·접근 불가·수동 검토로 분류한다.
4. 실제 삭제, 운영자 숨김, 중복 병합을 제외한 검증된 후보만 복구한다.
5. 변경 전후 상태·근거·실행 식별자를 남기고, 반복 실행해도 추가 변화가 없게 한다.
6. 공개 파일을 재생성해 목록·상세·검색에서 복구 결과를 확인한다.

**통과 기준**: 같은 입력 반복, 부분 탐색 반복, 원문 재등장 사례에서 정상 공지의 노출 상태가 보존된다. 후보 전체를 무조건 정상으로 돌리는 일괄 복구는 사용하지 않는다.

### 3단계 — 날짜 기반 과거 수집과 안전한 이어받기

**상태 설계**

기존 출처 상태와 초기 수집 상태를 구분한다. 아래 정보는 운영 데이터베이스에 영속 저장하며 정확한 열·테이블 배치는 구현 시 확정한다.

| 정보 | 의미 |
|---|---|
| 목표 시작일 | 기본 2026-03-01. 실행일 기준 상대 90일을 사용하지 않는다. |
| 범위 정책 버전 | 시작일·고정 공지·정렬 규칙 변경 시 이전 완료 상태를 재평가하는 기준 |
| 목록 도달 상태 | 미시작·진행 중·경계 도달·확인 불가 |
| 재개 위치와 기준 글 | 마지막 저장 완료 페이지·원문 번호·겹쳐 읽을 구간 |
| 확인 범위 | 가장 오래된 확인 날짜와 범위 경계의 근거. 날짜 최솟값만으로 완전성을 주장하지 않는다. |
| 상세 재시도 항목 | 원문 번호·주소·실패 사유·횟수·다음 시도·최종 결과 |
| 전체 완료 여부 | 목록 범위와 필수 상세 수집이 모두 충족된 경우만 참 |
| 마지막 진전 시각 | 계속 실행되지만 과거 범위가 전진하지 않는 출처 감지 |

**수집 규칙**

- 최신 확인은 첫 페이지에서 시작하고, 과거 채우기는 저장된 재개 위치를 기준으로 수행한다.
- 페이지 번호만 믿지 않는다. 앞 페이지에 새 글이 끼어드는 경우를 대비해 기준 글과 겹침 구간을 확인한다. 기준을 찾지 못하면 보수적으로 이전 구간부터 재탐색하고 미완료를 유지한다.
- 날짜순임이 검증된 게시판에서만 일반 글의 날짜 경계를 종료 근거로 사용한다. 고정 글은 경계 판단에서 분리한다.
- 날짜 미상·재정렬·과거 날짜의 신규 게시가 가능한 게시판에는 별도 탐색 규칙과 회전 재점검을 적용한다. 안전한 종료 근거가 없으면 상한에서 미완료로 남긴다.
- 현재 원문에서 고정된 글은 기간 밖이어도 우선 확보한다. 진행 여부가 불명확하면 임의로 만료 처리하지 않고 근거와 함께 남긴다.
- 기존 글 종료 판정은 누적 개수 대신 검증된 일반 글의 연속 구간과 겹침으로 구현한다. 과거 수집 미완료 상태에서 첫 페이지가 익숙하다는 이유로 과거 작업을 끝내지 않는다.
- 예산 소진 시 저장 완료 구간만 확정하고 다음 실행에서 이어간다. 개별 상세 실패가 목록 진전을 영구적으로 막지 않도록 재시도 항목을 따로 관리한다.
- 재시도 한도에 도달한 글은 확인 불가로 남기며 완료로 조용히 전환하지 않는다.

**통과 기준**: 중단 위치·새 글 삽입·날짜 미상·고정 글·상세 실패를 바꿔도 대상 원문 집합을 놓치지 않고, 미완료의 이유와 남은 작업을 조회할 수 있다.

### 4단계 — 최신 확인 우선 배정과 수집 비용 절감

**실행 순서**

- 최신 확인의 예정 시각과 마지막 시도를 기준으로 밀린 출처를 우선한다.
- 과거 작업에는 별도 시간·요청량 몫을 주고, 진전이 오래 없는 출처에 순환 기회를 준다.
- 지금처럼 식별자 순서에만 의존하지 않는다. 한 게시판이나 같은 서버의 느린 응답이 전체 순회를 차지하지 않게 한다.
- 시간·요청량·저장 연결 수를 각각 제한하고 내보내기에 필요한 여유 시간을 확보한다.

**요청·저장 최적화**

- 목록 한 페이지의 기존 원문 정보를 묶어서 조회한다.
- 신규, 목록 변경 신호, 상세 재시도, 재확인 예정 항목만 상세 요청한다.
- 최근 14일·고정·진행 중 공지는 하루 1회 재확인하고 오래된 원문은 회전 점검한다. 목록이 같다는 이유로 모든 과거 수정을 영원히 무시하지 않는다.
- 변경 여부 판단에는 제목·본문뿐 아니라 첨부·게시일 등 사용자에게 중요한 필드도 고려한다. 첨부만 바뀐 글이 기존 본문 해시 때문에 무시되지 않게 한다.
- 동일 내용의 원문 파일을 매회 다시 올리지 않는다. 기존 증거가 존재하는지와 추출기 버전을 고려하며, 증거 저장 실패 항목은 별도로 재시도한다.
- 원문 요청과 긴 대기 구간을 데이터베이스 트랜잭션 밖으로 분리한다. 항목 저장·연결 갱신·재개 상태 확정은 짧은 원자적 단위로 묶는다.
- 동기식 저장 작업은 제한된 별도 실행 자원으로 분리한다. 데이터베이스 세션을 여러 실행 흐름이 공유하지 않으며, 실패한 트랜잭션을 다음 항목에 재사용하지 않는다.
- 도메인이 달라도 같은 학교 서버를 공유할 수 있으므로 확인된 서버 묶음별 제한을 적용한다. 동시 처리 수를 일괄 상향하지 않고 응답 지연·차단·연결 사용량을 함께 측정한다.

**통과 기준**: 변화 없는 정기 순회에서 상세 요청과 원문 업로드가 재점검 대상 수준으로 줄고, 느린 출처가 있어도 다른 출처의 최신 확인과 과거 진전이 유지된다.

### 5단계 — 내보내기·검색·화면 계약 정리

- 첨부·원문 연결·연락처 언급을 공지별로 조회하지 않고 묶음 또는 일정 크기별로 읽는다. 조회 횟수와 최대 메모리를 함께 제한한다.
- 목록·상세·검색은 하나의 일관된 데이터 스냅샷에서 생성한다. 수집과 공개를 분리하더라도 개정 내부 데이터가 섞이지 않게 한다.
- 변경 없는 파일 재활용은 후속 최적화로 다룬다. 개정별 필수 파일이 빠지거나 이전 개정 참조가 끊기는 방식으로 업로드를 생략하지 않는다.
- 검색 색인의 8,000건 절단을 제거한다. 전체 항목을 담는 분할 색인과 목록 안내 파일을 도입하고, 화면은 필요한 분할을 읽되 검색 범위 미로딩을 결과 없음으로 오인하지 않게 한다.
- 현재 정적 제공 구조를 기준으로 프런트엔드가 최신 개정 안내 → 해당 개정의 자료를 읽도록 맞춘다. 검색·정렬·맞춤 필터·이어보기 기능도 함께 이식한다. 전량 본문 다운로드로 대체하지 않는다.
- 프런트엔드 조직 필터에 필요한 조직 연결 정보를 색인 계약에 포함한다. 현재 비어 있는 조직 값과 사용자 대상 조직을 혼동하지 않게 한다.
- 목표 시작일, 실제 확인 범위, 초기 수집 완료 여부, 미지원·오류 상태를 계약과 화면에 반영한다. 완료 전에는 목표 시작일만 표시해 해당 기간이 모두 있다는 인상을 주지 않는다.
- 수집 단계 결과, 공개 성공 여부, 실행 종료 결과를 나누어 기록하고 공개 상태에 최종 결과를 반영한다. 공개 실패 시 마지막 정상 개정과 실패 원인을 함께 식별할 수 있어야 한다.

**통과 기준**: 8,000건 초과 자료에서도 원문 대상과 공개·검색 집합이 일치하고, 새 개정 전환 중에도 페이지·상세·검색이 서로 다른 개정으로 섞이지 않는다.

### 6단계 — 미등록·미지원 출처 보완

- 호스트 판정은 링크를 실제 주소로 해석한 뒤 자기 사이트 또는 검증된 대표 주소의 구조를 근거로 수행한다. 외부 본부 링크 하나로 게시판 형식을 결정하지 않는다.
- 도서관·현장실습 사이트의 목록·상세·페이지 이동·고정·첨부 형식을 원문에서 확인하고 전용 수집기를 구현한다.
- 게시판 없음, 실제 빈 게시판, 구조 추출 실패, 미지원 형식을 서로 다른 상태로 기록한다.
- 탐색 미완료 13곳은 남은 메뉴를 이어 조사한다. 성격 미정 97개와 검토 대기 47개는 게시판 종류·상위 메뉴·실제 글을 근거로 판정한다.
- 휴면 514개는 목록 수준에서 새 글 발생 여부를 확인하고 필요한 게시판만 상세 조사한다. 반복 조사 결과와 다음 조사 예정일을 남긴다.
- 출처 중복 통합 시 대표 주소 변경이 기존 출처 식별자·원본·공지·구독을 끊지 않도록 이전 관계와 별칭을 보존한다.
- 생성기를 수정하고 등록부를 재생성한다. 운영 반영 전 추가·설정 변경·상태 전환·폐쇄 후보를 나눈 차이표를 검토하며, 운영자 보정과 중지 상태를 유지한다.

**통과 기준**: 조사 대상 각각에 등록·통합·제외·대기·접근 불가 중 하나의 근거가 남으며, 지원 실패가 정상 0건으로 집계되지 않는다.

### 7단계 — 운영 상태와 잔여 알려진 문제 정리

- 정상적으로 오래 실행 중인 작업과 죽은 작업을 구분할 수 있도록 실행 소유권·마지막 생존 시각·만료 기준을 설계한다. 로컬 실행과 예약 실행이 겹쳐도 같은 출처를 중복 처리하지 않게 한다.
- 고정 30분으로 기존 실행을 비정상 처리하지 않고 실제 실행 제한과 생존 정보에 맞춰 판정한다.
- 성공·부분 완료·실패에 출처 상세 실패와 초기 범위 미완료를 별도 수치로 포함한다. 과거 수집 중이라는 이유만으로 모든 정기 실행을 장애로 취급하지는 않는다.
- 최신 공지 반영 지연, 과거 범위 무진전, 반복 상세 실패, 공개 개정 정체를 각각 감지한다.
- 주소 변환망 문제는 변환 주소 안의 실제 IPv4 목적지를 검사하는 방식으로 수정하고 사설 주소 차단 검사를 유지한다. 이번 운영 지연 원인으로 확인되기 전에는 핵심 성능 개선과 분리한다.
- 만료되는 첨부 주소는 상세 재조회와 유효 주소 갱신 절차를 마련한다. 형제 도메인은 확인된 출처 설정에만 추가한다.
- 조직 이름 미확정 2곳은 공식 근거로 보완한다. 글 제목의 ‘후기’ 같은 낱말을 이용한 개별 공지 제외는 기존 결정대로 도입하지 않는다.
- 알려진 오류 문서의 상태·수치·검증 근거와 설정 문서·워크플로 주석을 실제 구현에 맞게 갱신한다.

## 6. 자동 검증과 실제 결과 검증

| 계층 | 필수 검사 | 합격 조건 |
|---|---|---|

성능 검사는 같은 자료·환경에서 수정 전후를 비교한다. 기존 계획의 신규 공지 2시간 내 반영을 운영 목표로 유지하되, 예약 지연을 포함한 실제 관측으로 달성 여부를 판단한다. 수집·내보내기 세부 목표와 과거 수집 완료 예상 시간은 1단계 측정 후 확정하며 지금 임의의 배속·완료 시각을 약속하지 않는다.

## 8. 데이터 이행·배포·되돌리기 순서

1. **기준 보존**: 배포 버전, 운영 설정, 복구 대상 상태, 최신 공개 개정과 백업 복원 가능성을 확인한다.
2. **추가형 구조 변경**: 새 상태·재시도 정보를 추가한다. 기존 완료 여부는 증거 없이 참으로 승격하지 않는다. 기존 코드와 공존 가능한 기간을 확보한다.
3. **삭제 보호 우선 적용**: 잘못된 판정 경로를 막고 대표 출처로 반복 수집·재발견을 검증한다. 이 단계 전에는 대량 과거 수집을 확대하지 않는다.
4. **수집·내보내기 개선 적용**: 제한된 출처에서 최신 확인·과거 재개·실패 복구·성능을 검증한다. 공개 계약은 기존 필드를 유지하는 추가형 변경부터 적용한다.
5. **공개 소비자 연결**: 새 파일 계약과 이를 읽는 화면을 호환되게 배포한다. 색인 형식을 바꾸면 기존 소비자가 읽는 자료를 호환 기간 동안 유지한다.
6. **검증된 피해 복구**: 후보 보고서를 기준으로 자동 삭제 피해를 복구하고 공개 결과를 대조한다.
7. **출처 확대와 과거 채우기**: 출처 묶음을 단계적으로 늘린다. 최신 지연·차단·저장 실패·무진전이 증가하면 확대를 중지한다.
8. **완료 감사**: 대상 출처별 범위와 예외, 공개·검색·화면 일치, 성능을 확인하고 알려진 오류 상태를 갱신한다.

되돌리기는 코드와 데이터에 따로 적용한다. 코드 문제가 있으면 호환 가능한 이전 버전으로 되돌리되 삭제 오판 보호는 유지한다. 잘못된 복구는 감사에 남긴 변경 대상만 되돌리고 이후 정상 변경을 덮어쓰지 않는다. 공개 문제는 유지 중인 정상 개정으로 안내를 되돌리고 짧은 캐시의 갱신을 확인한다. 새 상태 열은 즉시 제거하지 않는다.

확대 중지 조건은 정상 공지 오삭제, 설명되지 않는 누락, 개정 파일 불일치, 데이터베이스 연결 고갈, 원문 차단 증가, 최신 반영 목표의 반복 위반이다. 초기 수집 진행 중이나 설명된 접근 불가 자체를 무조건 되돌리기 조건으로 삼지는 않는다.

## 9. 작업 의존성과 최종 완료 보고

권장 순서는 **운영 기준 조사 → 삭제 보호 → 재개·성능 개선 → 공개 계약 검증 → 피해 복구·출처 확대 → 전체 감사**다. 출처 원문 조사와 화면 계약 설계는 삭제 보호 구현과 독립적으로 준비할 수 있지만, 대량 운영 실행은 삭제 보호와 재개 검증 후에 진행한다.

구현 전에 사용자의 선택이 반드시 필요한 새 제품 정책이 발견되면 해당 선택만 분리해 제시한다. 현재 확정된 시작일과 기간 밖 고정 공지 포함 원칙은 다시 묻지 않는다. 본 문서는 계획 작성 요청에 따른 것으로, 운영 실행이나 배포를 수행했다는 의미가 아니다.

최종 보고에는 다음을 반드시 포함한다.

- 대상 출처 수, 초기 범위 완료 수, 미완료·미지원·접근 불가 수와 이유
- 원문 대조 대상 건수, 설명되지 않는 누락 건수, 병합·제외 근거
- 잘못된 삭제 확인·복구·보류 건수와 감사 기록
- 수집·내보내기 단계별 수정 전후 시간·요청·조회량
- 최신 공지의 실제 화면 반영 지연과 관측 기간
- 적용 코드 버전·저장 구조 버전·공개 개정
- 정적·데이터·실행·운영 저장소·캐시·사용자 화면 검증 결과 및 미수행 계층
- 남은 알려진 문제와 후속 작업. 일부 검사 통과를 전체 완료로 표시하지 않는다.
