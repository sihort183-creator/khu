## 계획서 7.2절 1항이 통째로 구현되지 않았다 (16~19번)

`KHU_BACKEND_PLAN.md` 7.2절 1항은 이렇게 정해 두었다.

> 첫 등록의 초기 수집 범위는 **2026학년도 1학기 시작일(2026-03-01) 이후**를 기본으로 하되
> **진행 중 고정 공지는 기간 밖에서도 수집한다.**
> **기간·페이지 상한에 걸리면 수집 범위 미완료를 남긴다.**

세 가지 요구가 담겨 있는데 **셋 다 코드에 없다.** 아래 16·17·18번이 각각에 해당한다.
같은 절의 197행이 요구한 시작일 표시(19번)도 없다.

## 16. 초기 수집 범위(2026-03-01)가 구현되지 않았다 — 미결

수집기에는 날짜 경계가 아예 없다. 목록을 `list_page_limit`(기본 5)쪽까지 가져오고
멈출 뿐이다. "3월까지 거슬러 가서 멈춘다"는 판단을 하지 않는다.

3월까지 닿는지는 게시판마다 글이 얼마나 자주 올라오느냐에 달린 우연이다.
표본으로 잰 결과 5쪽이 거슬러 가는 기간은 중앙값 945일이고, 공지 게시판 801개 중
663개(82%)가 2026-03-01 까지 닿는다. **나머지 138개는 닿지 않는다.**
글이 잦은 본부·학사·취업 게시판이 여기에 몰려 있다.

**고칠 방법.** 쪽 수가 아니라 날짜로 멈춘다. 목록에서 읽은 게시일이 2026-03-01
이전으로 내려가면 그 출처는 범위를 다 채운 것이다. 페이지 상한은 안전장치로만 둔다.

## 17. 수집 범위 미완료를 기록하지 않는다 — 미결

계획서는 상한에 걸려 범위를 못 채우면 그 사실을 남기라고 한다.
`SourceHealth.backfill_complete` 칸이 **이미 만들어져 있는데 아무도 읽고 쓰지 않는다.**
스키마만 있고 로직이 없다.

그래서 지금 "어느 게시판이 어디까지 모였는지" 알 방법이 없다. 실행이 중간에
끊겼을 때 어디부터 이어가야 하는지도 알 수 없어, 매번 처음부터 다시 훑는다.

**고칠 방법.** 날짜 경계까지 닿았으면 `backfill_complete=True`, 상한에 걸려
멈췄으면 거짓으로 남긴다. 이미 채운 출처는 정상 순회만 하고, 못 채운 출처를
먼저 처리한다.

## 18. 고정 공지를 기간 밖에서 따로 수집하지 않는다 — 미결

계획서는 진행 중인 고정 공지(상단 고정)는 게시일이 범위 밖이어도 수집하라고 한다.

따로 챙기지 않는다. 날짜 경계(16번)를 넣을 때 함께 처리해야 한다.
그러지 않으면 2월에 올라와 지금도 유효한 고정 공지가 빠진다.

## 20. 죽은 실행이 "진행 중"으로 남는다 — 미결

## 15. 시간이 모자라 끊긴 회차가 멀쩡한 공지를 없어진 것으로 셌다 — 해결

**증상.** 실행 기록에 `연속 미발견으로 삭제 표시 40건` 이 여러 줄 남았다.
실제로 사라진 글이 아니었다.

**원인.** 회차가 끝날 때 "이번에 본 글 목록"과 저장된 글을 대조해 없어진 글을 센다.
그런데 시간 예산이 떨어져 목록을 중간에 끊은 회차에서는 **아직 안 본 글**도
목록에 없으니 사라진 글로 셌다. 한 번에 지우지는 않지만, 매 회차 같은 지점에서
끊기면 연속 미발견이 쌓여 멀쩡한 공지가 삭제 표시된다.

**고친 방법.** 목록을 끝까지 훑었는지를 따로 기록해, 그때만 없어진 글을 센다.
개별 글의 분석 실패(`detail_complete`)와는 구분한다. 그 경우 목록은 다 보았기 때문이다.

`tests/test_pipeline.py::test_budget_cut_run_does_not_mark_items_missing` 가 이를 붙잡는다.

## 14. 내보내기가 파일을 하나씩 올려 오래 걸린다 — 해결

**증상.** 13번을 고쳐 수집이 25분에 정확히 멈췄는데도 실행이 40분 타임아웃에 걸렸다.
멈춘 뒤 15분 동안 원문 요청이 하나도 없었다. 내보내기 단계가 그만큼 걸린 것이다.

**원인.** 공지 상세를 공지 수만큼 파일로 만들어 R2 에 **하나씩 차례로** 올렸다.
공지가 천 건을 넘으면 올릴 파일도 천 개가 넘는다.

**고친 방법.**
- 서로 의존하지 않는 파일(공지 상세·연락처 상세)을 한꺼번에 올린다.
  개정 포인터(`latest.json`)는 이 뒤에 따로 올리므로 순서는 그대로 지켜진다.
- boto3 연결 묶음을 16으로 올렸다. 기본값 10 이면 동시에 올릴 때 연결을 기다린다.

## 13. 수집이 시간 예산을 넘겨 강제 종료된다 — 해결

**증상.** 손으로 돌린 수집이 40분을 꽉 채우고 `cancelled` 로 끝났다. 워크플로의
`timeout-minutes: 40` 에 걸린 것이고, 30분으로 정해 둔 시간 예산이 듣지 않았다.

**원인.** 예산을 출처와 출처 사이, 목록 쪽과 쪽 사이에서만 확인했다.
한 게시판의 글을 하나씩 받는 안쪽 반복에는 확인이 없었다. 첫 수집처럼 새 글이
수십 건인 게시판에서는 글마다 서버 예의상 간격을 지키느라 이 반복만으로 예산을 넘긴다.

**고친 방법.**
- 글을 받는 안쪽 반복과 다음 쪽으로 넘어가기 전에도 예산을 확인한다.
  넘기면 남은 글은 다음 실행으로 미루고 `detail_complete` 를 거짓으로 남긴다.
- 예산을 1800초에서 1500초로 낮췄다. 40분 타임아웃 안에서 내보내기와 정리에
  15분을 남긴다.

**참고.** 출처가 78개에서 370개로 늘어 첫 몇 번은 예산을 다 쓰고 일부만 처리한다.
매시간 실행이 나누어 채우므로 정상이다. 새 글만 받게 되면 빨라진다.

## 12. 두 번째 수집부터 중복 키로 죽는다 — 해결

**증상.** 예약된 매시간 수집이 계속 실패한다.

```
psycopg.errors.UniqueViolation: duplicate key value violates unique constraint "pk_dedupe_decisions"
DETAIL:  Key (id)=(b354d3a40987) already exists.
```

**원인.** [`repository.record_dedupe_decision()`](../backend/app/storage/repository.py) 이
중복 판정 기록의 열쇠를 `_digest(좌항목, 우항목, 좌개정, 우개정)` 으로 만든다.
입력이 같으면 열쇠도 같다. 같은 두 글을 다음 실행에서 다시 비교하면 같은 열쇠로
새로 넣으려 하고, 그 자리에서 실행 전체가 멈춘다.

[`collect.py`](../backend/app/run/collect.py) 의 `seen_pairs` 는 **한 번의 실행 안에서만**
같은 쌍을 거른다. 실행과 실행 사이는 막지 못한다.

**영향 범위.** 첫 수집은 지나가고 두 번째부터 막힌다. 지금 예약 실행이 매시간 실패하고 있다.
글을 가져오는 데까지는 성공하고 중복 판정을 적는 단계에서 죽는다.

**고친 방법.** `session.add()` 를 `session.merge()` 로 바꿨다. 같은 열쇠가 이미 있으면
새로 넣지 않고 갱신한다. 판정을 다시 해도 같은 사실이라 갱신이 맞다.
`merge()` 는 PostgreSQL 과 SQLite 에서 같게 동작한다.

`tests/test_repository.py::test_same_dedupe_pair_can_be_recorded_twice` 가 이를 붙잡는다.
`merge()` 를 `add()` 로 되돌리면 이 검사가 실패한다.

**쓰지 않은 방법.** 열쇠에 시각을 넣어 매번 다르게 만들면 중복은 피하지만
같은 판정이 실행 횟수만큼 쌓인다.

## 1. NAT64 회선에서 SSRF 방어가 정상 주소를 막는다 — 미결

**증상.** 핫스팟 같은 IPv6/NAT64 망에서 검사 18개가 실패한다.

```
BlockedRequest: [blocked_target] 예약된 주소로 해석됨: www.khu.ac.kr -> 64:ff9b::af6a:5661
```

**원인.** NAT64 망은 IPv4 주소를 `64:ff9b::/96` 아래로 매핑해 돌려준다.
`www.khu.ac.kr` 은 `175.106.86.97` 과 `64:ff9b::af6a:5661` 두 가지로 해석되는데,
뒤엣것은 앞엣것을 그대로 감싼 같은 목적지다. 그런데
[`backend/app/ingestion/http.py`](../backend/app/ingestion/http.py) 의 `_ip_is_public()` 이
이를 예약 주소로 보고 막는다.

**영향 범위.** 회선에 달렸다. 일반 유선·와이파이에서는 재현되지 않고 검사도 모두 통과한다.
GitHub Actions 는 IPv4 라서 지금 운영에는 영향이 없다. 다만 나중에 IPv6 전용 환경에서
수집을 돌리면 아무것도 가져오지 못한다.

**왜 아직 안 고쳤나.** SSRF 방어는 보안 코드라 조심해서 손대야 한다.
`64:ff9b::/96` 을 그냥 통과시키면 안 되고, **감싸고 있는 IPv4 주소를 꺼내어 그 주소로
다시 검사**해야 한다. 그래야 NAT64 를 거쳐 사설망을 찌르는 요청을 계속 막을 수 있다.

**고칠 때 할 일.**
- `64:ff9b::/96` 에 드는 주소는 하위 32비트를 IPv4 로 바꿔 `_ip_is_public()` 을 다시 태운다.
- NAT64 로 감싼 사설 주소(예: `64:ff9b::c0a8:1` → `192.168.0.1`)가 막히는지 검사를 추가한다.

이 호스트들만 골라 상한을 올려 다시 돌리면 된다.

```bash
python scripts/discover_sources.py --hosts ois.khu.ac.kr bme.khu.ac.kr --page-budget 500
```

상한을 올리면 그만큼 통신량이 늘어난다(11번 참고).

## 5. 조직 이름을 못 찾은 사이트 2곳 — 미결

`www.khu.ac.kr` 과 `news.khu.ac.kr` 은 사이트 명부에도 없고 페이지 제목도 `경희대학교` 뿐이라
공식 이름을 확인하지 못했다. `organizations.json` 에 `needs_review: true` 와
`[확인 필요]` 표시로 남아 있다. **이름을 지어내지 않는다**는 원칙에 따른 것이다.
학교 조직도에서 확인해 손으로 채우면 된다.

## 6. 휴면 게시판 503개는 학기가 바뀌면 살아날 수 있다 — 미결

마지막 글이 2년 넘게 없는 게시판을 `dormant` 로 두고 출처에서 뺐다.
학기가 시작되면 다시 글이 올라오는 곳이 있을 수 있다.
학기마다 하는 재조사에서 자동으로 다시 판정되므로 따로 손댈 필요는 없지만,
**재조사를 거르면 이 게시판들은 계속 빠진 채로 남는다.**

## 7. 그누보드 첨부 주소가 형제 도메인으로 나가고 만료된다 — 미결

`khugpp.khu.ac.kr` 의 첨부 내려받기 주소는 `gpp.khu.ac.kr` 로 나가고, 만료되는 `nonce` 를 달고 있다.

```
https://gpp.khu.ac.kr/bbs/download.php?bo_table=notice&wr_id=17&no=0&nonce=...
```

두 가지가 걸린다.

- 첨부를 실제로 받으려면 출처 설정의 `allowed_hosts` 에 `gpp.khu.ac.kr` 을 함께 적어야 한다.
  적지 않으면 SSRF 검사에서 막힌다.
- `nonce` 는 시간이 지나면 무효가 된다. 저장해 둔 주소로 나중에 다시 받을 수 없다.

지금은 주소를 원문 그대로 보관만 하고 있다. 검사
`tests/test_adapter_gnuboard.py::test_parses_legacy_detail_with_attachments` 가 이 성질을 붙잡아 둔다.

## 8. 글 단위로 후기·사진을 걸러내지 않는다 — 해결(넣지 않기로 결정)

걸러내기는 **게시판 단위로만** 한다. 공지 게시판 안에 개별 후기·사진 글이 섞이는 것은 그냥 둔다.

그렇게 정한 이유는 낱말이 겹치기 때문이다. `후기` 는 후기(後記)보다 **학기 표기**로 훨씬 많이 쓰인다.

- `2026학년도 **후기** 경영대학원 신·편입생 모집 안내` ← 2학기라는 뜻이다
- `2025학년도 **후기** 졸업대상자 학위가운 대여 안내` ← 마찬가지다

낱말로 글을 거르면 이런 진짜 공지를 버린다. 잘못 버린 것은 되돌릴 수 없고,
게시판 단위에서 이미 잡음의 대부분(게시판 1,531개)을 걷어냈다.
수집한 자료가 쌓인 뒤에 다시 판단한다.

## 9. 게시판 이름으로 공지를 고르면 안 된다 — 해결

예전 등록부 생성기는 게시판 이름에 `공지|알림|소식` 같은 낱말이 있는지로 골랐다. 이 방식은 틀린다.

국제처(`oia.khu.ac.kr`)가 근거다. `Outgoing Program` 에는 마감이 있는 교환학생 모집 공고가
올라오고, `News` 에는 행사 후기만 올라온다. 이름만 보면 정확히 거꾸로 고른다.

지금은 `board_code`(게시판 종류) → 상위 메뉴 → 최근 글 순서로 판정한다.
자세한 것은 [`SOURCE_DISCOVERY.md`](SOURCE_DISCOVERY.md) 에 있다.

## 10. 사이트 명부의 도메인 칸이 실제와 다른 곳이 있다 — 해결

학교 사이트 가이드는 국제처를 `oiak.khu.ac.kr` 로 적어 두었지만 실제 사이트는
`oia.khu.ac.kr` 에 있다. 명부만 믿으면 국제처 공지가 통째로 빠진다.

`discover_hosts.py` 가 명부와, 사이트들이 서로 링크한 주소를 **합쳐서** 확인한다.
이 덕분에 취업(`goodjob`)·학사(`ghaksa`/`shaksa`)·의과대학(`khusm`)·법학전문대학원(`law`)이 들어왔다.

**명부에 없는 사이트가 더 있을 수 있다.** 어느 사이트도 링크하지 않는 곳은 이 방법으로도 못 찾는다.

## 11. 조사 통신량이 크다 — 해결(줄이는 방법 마련)

경희대 서버는 압축을 하지 않는다. `Accept-Encoding: gzip` 을 보내도 `Content-Encoding` 이
없고 그대로 온다. 페이지 하나가 평균 87KB 다.

| 단계 | 요청 | 내려받은 양 |
| --- | ---: | ---: |
| 게시판 탐색(160개 호스트) | 8,798 페이지 | 약 747MB |
| 게시판 성격 조사(2,335개) | 2,335 페이지 | 약 200MB |

조사는 실행하는 기기의 통신을 그대로 쓴다. **데이터 요금이 있는 회선에서는 돌리기 전에 확인한다.**

판정 규칙만 고칠 때는 통신이 필요 없다. 표본이 이미 파일에 있다.

```bash
python scripts/profile_boards.py --reclassify registry/bootstrap/board_profiles.json
```
