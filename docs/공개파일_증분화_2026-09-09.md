# 공개 파일 만들기를 증분으로 바꾼다 (2026-09-09)

2026-09-09 Supabase 가 **egress(데이터베이스에서 나간 데이터) 무료 한도 월 5 GB 초과**를
알려 왔다. 10월 9일부터 제한이 걸릴 수 있다. 가장 큰 몫은 매시간 도는 공개 파일
만들기(`backend/app/export/static.py`)였다. 보이는 공지 전부를 **본문까지** 다시 읽어
같은 파일을 다시 만들고 있었다.

이 문서는 그것을 증분으로 바꾼 내용을 적는다. 숫자는 모두 운영 데이터베이스에서
직접 잰 값이다. 추정한 것은 추정이라고 적었고, 재지 못한 것은 마지막 절에 모았다.

**이 작업에서 운영 데이터베이스에 쓴 것은 없다. 운영 R2 에도 쓰지 않았다.**
확인 실행은 로컬 폴더 저장소(`LocalObjectStore`)로만 했다.

목록 쪽 하나다(4절).

## 2. 설계

### 2.1 매 회차 하는 일

```
① 가벼운 전체 훑기      공지 id · 수정 시각 · 현재 개정 id 만 전부 읽는다 (약 1.5 MB)
② 이전 판 받아 오기     R2 에서 지난 개정의 기록과 명세를 받는다 (R2 는 나가는 데이터 무료)
③ 견주어 계획 세우기    새 것 · 바뀐 것 · 사라진 것 · 그대로인 것을 정확히 가른다
④ 바뀐 것만 본문 읽기   그대로인 공지는 본문을 한 글자도 읽지 않는다
⑤ 만들기               목록·색인·공유 정보는 매번 새로 만들고, 상세 파일은 물려받는다
```

③에서 **추측하지 않는다.** "이쯤 바뀌었겠지"가 아니라 이전 판의 수정 시각·개정 id 와
이번 훑기의 값을 하나씩 견준다.

### 2.2 상세 파일을 물려받는 방법

공개 파일은 이미 **내용 주소 방식**이다. 파일 내용에서 회차마다 달라지는 값(meta,
revision, generated_at, freshness)을 빼고 남은 몸통의 SHA-256 이 곧 객체 이름
(`v1/objects/<sha256>.json`)이고, 개정 명세(`manifest.json`)가 공개 경로와 그 객체를
잇는다. Worker 는 명세를 보고 응답을 합성한다.

그래서 내용이 같은 공지는 **새 명세에 같은 객체 이름을 적어 넣기만 하면 된다.**
파일을 내려받을 필요도, 다시 올릴 필요도 없다(`Writer.carry`).

이 성질은 검증에도 그대로 쓰인다. **두 개정 명세의 값이 같다 = 두 개정이 만든 파일이
바이트 단위로 같다.** 그림자 대조(2.5절)와 자체 점검이 이 사실 위에 서 있다.

### 2.3 목록 항목은 기록에 담아 둔다

목록 파일에는 제목·발췌·분류·대상·대표 그림이 들어간다. 이 값들을 회차마다 다시
읽으면, 본문을 하나도 안 읽어도 회차당 20 MB 를 넘는다(3절 표). 그래서 **이전 회차의
목록 항목을 그대로 기록에 담아 두고**, 바뀌지 않은 공지는 그것을 다시 쓴다.
기록은 개정마다 하나씩 R2 에 둔다(`v1/state/<개정>.json`, 실측 4.4 MB gzip).
회차마다 그만큼 쌓이므로 회차 끝에 최근 3개만 남기고 지운다(`prune_export_state`).

기록은 `manifest.json` 이 **아니라** 따로 둔다. 명세는 Worker 가 조회 요청마다
받아 읽는 파일이라 무겁게 만들면 안 된다.

물려받은 항목이라도 **신선도(freshness)는 이번 회차 값으로 갈아 끼운다.** 신선도는
파일 안이 아니라 명세에 실리는 값이라, 낡은 값을 물려주면 화면의 "마지막 확인"이 멈춘다.

### 2.4 이전 판을 못 믿게 되는 경우 — 지문과 자동 후퇴

공지 파일 안에는 그 공지 것이 아닌 값도 들어간다. 출처 이름, 조직·캠퍼스 이름,
공개 하한, 그림 중계 주소가 그렇다. 이것들을 묶어 지문(fingerprint)을 만들고 기록에
남긴다. 지문이 달라지면 그 회차는 전체 방식으로 돈다.

지문에는 **배포한 코드 판(`GITHUB_SHA`)도 넣는다.** 내보내기 코드를 고쳐 놓고 판을
올리는 것을 잊으면 낡은 파일이 조용히 살아남기 때문이다. 배포 뒤 첫 회차 한 번만
전체로 돌면 된다.

전체 방식으로 되돌아가는 조건은 다음과 같다. 이유는 로그와 실행 기록(run note)과
회차 기록에 남는다.

| 조건 | 이유 문구 |
|---|---|
| `KHU_EXPORT_MODE=full` | 전체 방식 요청 |
| 이전 판 기록을 못 받아 옴 / 비어 있음 | 이전 판 기록이 없음 |
| 지문이 다름(출처·조직·설정·코드) | 공유 정보(출처·조직·설정·코드)가 바뀜 |
| 이전 개정 명세를 못 받아 옴 | 이전 개정 명세를 받지 못함 |
| 하루 한 번 강제 재생성 | 하루 한 번 전체 재생성 — … |
| 바뀐 공지 비율이 임계 초과(기본 30%) | 바뀐 공지 N건이 전체 M건의 …%로 임계(30%)를 넘음 |

공지 하나 단위의 후퇴도 있다. 물려받으려는 상세 파일이 이전 명세에 없거나, 그 내용
객체가 R2 에 실제로 없으면 **그 공지만** 다시 만든다.

원문 날짜가 미래인 공지(고정 공지에 2099-12-31 같은 값을 쓰는 게시판)는 시간이 지나면
보이는 날짜가 저절로 달라진다. 수정 시각은 그대로이므로, 이런 공지는 늘 다시 만든다.

### 2.5 그림자 대조와 하루 한 번 전체 재생성

- **그림자(shadow)**: 전체 방식으로 만들어 공개하고, 같은 회차에 증분 방식도 돌려
  두 개정 명세를 견준다. 어긋난 파일 수와 예시를 회차 기록에 남긴다.
- **하루 한 번 전체 재생성**: KST 04시 이후 첫 회차(그리고 마지막 전체 재생성이
  26시간을 넘으면 그때)는 전체로 돈다. 이 회차에서는 **그림자 대조도 함께 돈다**.
  추가로 드는 데이터베이스 읽기는 가벼운 훑기뿐이라 사실상 공짜다.
  즉 증분으로 운영해도 하루에 한 번은 전체와 대조된다.

## 3. 잰 값과 근거

방법: 운영 데이터베이스에 **읽기 조회만** 보냈다. 본문 크기는 서버 쪽 집계
(`octet_length`, `sum`)로만 쟀다. 회차당 읽기량은 새로 만든 계측(6절)으로 쟀다.

### 3.3 전체 방식에서 그냥 낭비하던 것

열을 골라 읽도록 고치면서 다음이 사라졌다. **증분과 무관하게, 전체 방식에서도 준다.**

| 뺀 것 | 회차당 |

## 4. 확인 결과

### 4.1 자동 검사

`backend` 의 pytest **340개 전부 통과**(전에는 300개, 새로 40개 늘었다).

    cd backend
    PYTHONIOENCODING=utf-8 .venv/Scripts/python -m pytest -q -W "ignore::DeprecationWarning"

`-W "ignore::DeprecationWarning"` 은 **로컬 파이썬이 3.14** 라서 붙인다. pytest-asyncio
0.24 가 3.14 에서 없어진 `asyncio.iscoroutinefunction` 을 부르는데, `pyproject.toml` 의
`filterwarnings = ["error::DeprecationWarning"]` 이 그것을 오류로 올려 수집 단계에서
멈춘다. **CI 는 파이썬 3.12 라 이 옵션 없이 그대로 돈다.** 코드 문제가 아니다.

새로 넣은 검사(40개)가 덮는 것:

| 파일 | 무엇 |
|---|---|
| `tests/test_export_incremental.py` (25개) | 명세 비교(새·바뀐·사라진), 개정 id 이동, 미래 날짜 공지 재생성, 자동 후퇴 6가지, 하루 한 번 판정 4가지, 종단(증분 결과 = 전체 결과), 새 공지·숨긴 공지, 범위 밖 공지 기억, 그림자 일치/불일치, 강제 전체 재생성의 대조, 알 수 없는 방식, 회차 기록, 오래된 기록 정리 |
| `tests/test_db_read_meter.py` (4개) | 고른 열만 세는가, 누적·초기화, 두 번 켜도 두 번 세지 않는가, 계측이 결과를 바꾸지 않는가 |

| `tests/test_selfcheck.py` (+5개) | 「증분·전체 일치」 항목의 이상/정상/기록 없음/기록 낡음 |

특히 `test_shadow_mode_reports_a_mismatch_when_the_previous_edition_went_stale` 은
**수정 시각을 올리지 않고 본문만 바꾼** 상황을 만들어, 그림자 대조가 그것을 실제로
잡아내는지 본다. 트리거가 막으려는 바로 그 고장이다.

### 4.2 운영 자료로 한 번 확인

**본문 전체를 읽는 실행은 딱 한 번만 했다.** 그 한 번이 위 3.4 표의 "전체" 열이다
(69.94 MB). 이어서 증분 회차를 한 번 돌렸다(2.23 MB). 둘 다 로컬 폴더 저장소에
썼고 운영 R2 는 건드리지 않았다.

두 회차의 개정 명세를 견준 결과:

| | 값 |
|---|---:|
| 전체 회차가 만든 파일 | 24,314 |
| 증분 회차가 만든 파일 | 24,314 |
| 한쪽에만 있는 파일 | 0 |
| 값이 다른 파일 | **2** (`notices/ntc-3071cf54451e.json`, `notices/page/12.json`) |

다른 2개는 두 회차 사이 2분 동안 수집이 공지 12건을 건드렸고 그중 하나의 내용이
실제로 달라졌기 때문이다(증분 회차의 "다시 읽은 공지 12건"과 맞는다). 즉 **어긋남이
아니라 증분 쪽이 더 최신인 것**이다.

이 대조가 값진 이유: 목록 쪽과 색인은 증분 회차에서 **기록에 담아 둔 항목**으로 다시
만든 것이다. 그것이 데이터베이스에서 새로 읽어 만든 것과 바이트 단위로 같다는 뜻이다.

**그림자 방식(`shadow`)을 운영 자료로 돌리지는 않았다.** 그러려면 본문 전체를 한 번 더
읽어야 해서(약 70 MB) 그만두었다. 그림자 대조 자체는 위 검사 25개 중 3개가 덮는다.

### 4.3 트리거 마이그레이션은 문법 검증까지만 했다

이 컴퓨터에 PostgreSQL 도 Docker 도 없다(`docker`·`psql` 모두 없음). 그래서
**트리거가 실제로 발화하는 것은 확인하지 못했다.** 확인한 것은 SQLite 에서의
upgrade/downgrade 와 SQL 문자열의 구조(6개 검사, 4.1절)다. 실제 확인 방법은 7.3절.

## 6. 계측 인터페이스 (`backend/app/storage/db.py`)

수집 단계 측정에도 그대로 쓰라고 만든 것이다.

```python
from app.storage.db import (
    ReadStats, enable_read_meter, disable_read_meter,
    read_stats, reset_read_meter, measure_reads,
)

enable_read_meter()          # 켠다. 엔진을 주지 않으면 전역 엔진에 붙는다. 여러 번 불러도 한 번만 붙는다.
disable_read_meter()         # 뗀다. 누적값은 지우지 않는다.
reset_read_meter()           # 누적값을 0으로.
stats = read_stats()         # ReadStats(statements, rows, bytes) — 누적

with measure_reads() as measured:      # 구간 측정. 꺼져 있으면 자동으로 켠다.
    ...
measured[0].bytes                      # 구간이 끝나야 값이 정해진다(그래서 한 칸짜리 목록)

before = read_stats()
...
delta = read_stats().delta(before)     # 임의 구간
stats.as_dict()                        # {"statements":…, "rows":…, "bytes":…}
```

**어떻게 재나.** SQLAlchemy 의 `after_cursor_execute` 에서 DBAPI 커서를 얇은 대리자로
바꿔치기하고, 실제로 꺼내 가는 행의 값 길이를 더한다(문자열은 UTF-8 바이트, `bytes` 는
그 길이, 나머지는 8바이트로 셈). 결과·트랜잭션·예외 처리에는 손대지 않는다.
대리자를 못 붙이면 계측만 조용히 포기하고 조회는 그대로 간다.

**근사치다.** 실제 회선 위에는 열 이름·형식 정보·프로토콜 덮개가 더 붙으므로 이 값은
**하한에 가깝다.** 반대로 서버 쪽 `row::text` 집계는 따옴표·이스케이프가 붙어 약 13%
크게 나온다(`docs/수집_읽기량_측정_2026-09-09.md`). 절대값보다 **같은 방법으로 잰
전후 비교**에 쓰라고 만든 값이다.

**어디에 남나.**
- 내보내기 단계: `ExportResult.db_read_bytes / db_read_rows / db_read_statements`
- 회차 전체: `runs.note` 에 `DB 읽기 12.3MB(공개 2.2MB, 방식 incremental, 물려받은 상세 22826개)`
- 회차 기록: `.localstore/export-metrics.json` 과 `v1/state/export-metrics.json`

## 7. 운영 절차

### 7.1 순서

1. **마이그레이션 적용.** `.github/workflows/migrate.yml` 을 사람이 실행해 `0004` 를
   올린다. 코드가 기대하는 판이 `0004` 이므로, **코드가 먼저 배포되면 수집이
   `SchemaMismatch` 로 멈춘다.** 마이그레이션을 먼저 하거나, 배포 직후 바로 한다.
2. **shadow 로 관찰.** 저장소 변수 `KHU_EXPORT_MODE=shadow`. 공개되는 것은 지금까지와
   똑같은 전체 방식 결과이므로 화면에는 아무 변화가 없다. 자체 점검의
   「증분·전체 일치」가 며칠 연속 정상인지 본다.
   **비용 주의**: shadow 는 전체 방식과 같은 양(회차당 약 70 MB)을 읽는다. 며칠만 둔다.
3. **incremental 로 전환.** `KHU_EXPORT_MODE=incremental`. 회차당 약 2 MB 로 떨어진다.
   하루 한 번 도는 전체 재생성 회차가 계속 대조를 해 준다.
4. **되돌리기.** 저장소 변수 `KHU_EXPORT_MODE` 를 `full` 로 바꾸거나 지운다.
   push 도 배포도 필요 없고, 다음 회차부터 지금까지의 방식으로 돌아간다.

### 7.2 저장소 변수

| 변수 | 기본 | 뜻 |
|---|---|---|
| `KHU_EXPORT_MODE` | `full` | `full` / `shadow` / `incremental` |
| `KHU_EXPORT_MAX_CHANGED_RATIO` | `0.3` | 바뀐 공지가 이 비율을 넘으면 그 회차는 전체로 |
| `KHU_EXPORT_FULL_EVERY_HOURS` | `24` | 강제 전체 재생성 간격 |
| `KHU_EXPORT_FULL_HOUR_KST` | `4` | 그 재생성을 이 시각(KST) 이후 첫 회차에서 |

알 수 없는 값을 넣으면 경고를 남기고 `full` 로 돈다.

### 7.3 트리거 마이그레이션을 로컬에서 확인하는 방법

이 작업에서는 PostgreSQL 이 없어 하지 못했다(4.3절). 확인하려면:

```bash
# 1) 빈 PostgreSQL 을 띄운다 (16 이상이면 된다. 전이 표는 10부터 있다)
docker run --rm -d --name khu-pg -e POSTGRES_PASSWORD=pw -p 55432:5432 postgres:16

# 2) 빈 스키마에 마이그레이션을 끝까지 올린다
cd backend
KHU_DATABASE_URL='postgresql://postgres:pw@localhost:55432/postgres' \
  .venv/Scripts/python -m alembic -c alembic.ini upgrade head

# 3) 트리거가 붙었는지 본다 (16개)
docker exec khu-pg psql -U postgres -c \
  "select tgname, tgrelid::regclass from pg_trigger where not tgisinternal order by 2,1;"

# 4) 실제로 발화하는지 본다 — 공지 하나를 넣고 분류를 바꿔 updated_at 이 오르는지
docker exec khu-pg psql -U postgres -c "
  insert into universities(id,code,name) values('u','khu','경희대학교');
  insert into organizations(id,university_id,org_type,name) values('o','u','office','본부');
  insert into sources(id,organization_id,name,adapter,list_url)
    values('s','o','시험','khu_board','https://example.invalid/');
  insert into source_items(id,source_id,external_id,canonical_url)
    values('i','s','1','https://example.invalid/1');
  insert into source_item_revisions(id,source_item_id,content_hash,title,extractor_version)
    values('r','i','h','제목','t');
  update source_items set current_revision_id='r' where id='i';
  insert into notices(id,primary_source_item_id,title,updated_at)
    values('n','i','제목', timestamptz '2020-01-01');
  insert into notice_categories(id,notice_id,category_code,is_primary)
    values('c','n','other',true);
  select updated_at > timestamptz '2020-01-02' as 올랐나 from notices where id='n';
"

# 5) last_seen_at 만 바꿔서는 오르지 **않아야** 한다
docker exec khu-pg psql -U postgres -c "
  update notices set updated_at = timestamptz '2020-01-01' where id='n';
  update source_items set last_seen_at = now() where id='i';
  select updated_at = timestamptz '2020-01-01' as 그대로인가 from notices where id='n';
"

# 6) 되돌리기
KHU_DATABASE_URL='postgresql://postgres:pw@localhost:55432/postgres' \
  .venv/Scripts/python -m alembic -c alembic.ini downgrade 0003
docker exec khu-pg psql -U postgres -c \
  "select count(*) from pg_proc where proname like 'khu_touch%';"   -- 0 이어야 한다
docker rm -f khu-pg
```

### 7.4 트리거가 하는 일과 일부러 뺀 것

| 표 | 방식 | 언제 |
|---|---|---|
| `notice_categories`, `notice_audiences`, `notice_sources` | 문단위(전이 표) | 넣기·고치기·지우기 |
| `attachments`, `notice_contact_mentions` | 문단위(전이 표) | 넣기·고치기·지우기 (개정 → 원본 → 공지로 거슬러 올라간다) |
| `source_items` | 행 단위 + WHEN | `current_revision_id`·`canonical_url`·`original_status`·`is_pinned` 가 달라졌을 때만 |
| `source_item_revisions` | 행 단위 + WHEN | `body_html`·`body_text`·`title`·`published_date` 를 제자리에서 고쳤을 때만 |

**`source_items.last_seen_at` 은 일부러 뺐다.** 회차마다 거의 모든 행이 바뀌는 값이라,
그것까지 세면 매 회차 전부가 "바뀐 공지"가 되어 증분이 무의미해진다. 행 단위 트리거에
WHEN 조건을 단 이유가 이것이다.

적용한 뒤에는 다음 조회로 부작용을 확인하는 것이 좋다. 값이 갑자기 수천 건으로 뛰면
어딘가에서 의도치 않은 갱신이 일어나고 있다는 뜻이다.

```sql
select count(*) from notices where updated_at >= now() - interval '1 hour';
-- 2026-09-09 기준(트리거 적용 전): 1시간 0건, 3시간 54건, 24시간 413건
```

## 8. 확인하지 못한 것

- **트리거가 실제로 발화하는지 확인하지 못했다.** 이 컴퓨터에 PostgreSQL 도 Docker 도
  없다. 확인한 것은 SQLite 에서의 upgrade/downgrade 와 SQL 문자열의 구조뿐이다.
  7.3절의 절차로 확인해야 한다.
- **트리거가 수집 회차의 쓰기 부하를 얼마나 늘리는지 재지 못했다.** 문단위 트리거라
  대량 작업에서도 문장당 한 번이지만, 실제 증가분은 적용 뒤에 봐야 한다.
- **트리거 적용 뒤에 "바뀐 공지" 비율이 얼마가 되는지 모른다.** 지금(트리거 없음)은
  24시간에 1.7%다. 트리거가 붙으면 늘어난다. 임계 30%를 넘길 정도라고 볼 근거는
  없지만, 재 보지 않았다.
- **운영 자료로 그림자 방식을 돌려 보지 않았다.** 본문을 한 번 더 읽어야 해서다.
  대신 전체 회차와 증분 회차의 명세를 견주었다(4.2절).
- **회선 위의 실제 바이트를 재지 못했다.** 계측도 서버 쪽 집계도 근사치다.
  Supabase 가 세는 값과 정확히 같다는 보장은 없다. 증감의 방향과 규모는 믿을 만하다.
- **Worker 를 배포해 확인하지 못했다.** `v1/state/` 를 막는 한 줄만 고쳤고, 배포하지
  않아도 동작에 문제는 없다(그 경로가 그냥 공개될 뿐이며, 담긴 값은 이미 공개된
  제목·발췌·식별자다).
- 3.5절의 한 달 환산은 회차 빈도 가정에 기댄 값이다. 실제 빈도는 달라진다.
